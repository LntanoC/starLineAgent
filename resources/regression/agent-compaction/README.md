# 比特严选记忆摘要回归

[返回回归总览](../README.md)

本套件在已启动的 StarlineAgent 上，用比特严选人设跑几条约 130 轮的长会话，逐代读出库里的上下文压缩摘要，回答两个问题：

1. **摘要有没有界**：每代字数在不在区间里；所有事项都进过摘要之后，相邻两代还涨不涨；压缩后上下文有没有回落。
2. **摘要是否满足已实现的规则**：检查订单号、暂缓、放弃、条件、用户声称等固定剧本规则。语义检查主要是词法启发式，PASS 不保证事实关系正确。工具查询详情按提示词约定不保留，只留单号和型号，接手时重新查询。另外记录主 Agent 的弹卡行为。

判定使用每代摘要、已保存的实际用户消息、每轮确认卡以及整次运行的业务库写入计数。不问模型「你还记得吗」。业务规则在对应原话被压出原文之后才生效；还留在原文里的事，摘要可以不写。

## 前提与范围

这是一套长会话压力回归，重点检查反复问答后的长度、限制和状态继承；通过不代表整个客服摘要功能已全面验收。

- Java 17+。StarlineAgent（默认 9090）、PostgreSQL、MCP 服务都已启动。当前激活的人设必须是 `比特严选 Agent`。
- 服务地址、平台库账号、上下文预算来自 `bootstrap/src/main/resources/application.yaml`；业务库账号来自 `mcp-server/src/main/resources/application.yml`。
- 默认用 `admin/admin` 登录，订单 88232 挂在这个账号名下。
- 开跑前会逐槽位比对库里的提示词与 `initializer/bit-selection/prompts/`，不一致就拒跑。否则结论说的是另一份提示词。
- 确认卡一律拒绝，不办任何真事。开跑前后各数一次该账号的工单与售后单，有增加即判失败。
- 会话留在 admin 的侧栏里，不自动删除。真实模型调用会正常计费：两条会话并行，各跑约 110 轮，整轮四十多分钟。

本剧本未覆盖的两个场景：

- **放行状态经过压缩后仍被正确保留**：第 80 轮放行、第 82 轮再次暂缓；已核对的两轮 v18 实跑（`20261006-134552`、`20261006-170925`）没有一代摘要的压缩范围恰好停在第 80～81 轮。第 80 轮弹卡，只证明主 Agent 当时读到放行，不代表摘要保住了放行。
- **办理成功后的压缩**：所有确认卡都会被拒，因此本剧本只能检查未执行、被取消和虚构完成，不能验证实际成功的办理结果如何继承。这两项需要单独的短快照用例，不通过延长本剧本补齐。

## 运行

从仓库根目录执行：

```bash
# 离线检查判定器：正反例、否定与撤回、连续失败统计、空目录，不调用模型或数据库
bash resources/regression/agent-compaction/run.sh --self-test

# 完整回归：默认 2 条并行会话，产物在 artifacts/时间戳/
bash resources/regression/agent-compaction/run.sh

# 冒烟：1 条会话只跑前 3 轮，只验链路，不能下结论
bash resources/regression/agent-compaction/run.sh --sessions 1 --limit 3

# 只改了判定规则：拿已有产物重判，不重跑
bash resources/regression/agent-compaction/run.sh --evaluate resources/regression/agent-compaction/artifacts/<时间戳> \
  --output-dir resources/regression/agent-compaction/artifacts/<时间戳>-review

# 只改了压缩提示词：拿实跑产物离线重放，几分钟出报告，--repeat 每条会话多重放几遍
bash resources/regression/agent-compaction/run.sh --replay resources/regression/agent-compaction/artifacts/<时间戳> --repeat 2
```

`--evaluate` 不覆盖源报告。省略 `--output-dir` 时，在源目录旁新建 `<源目录>-evaluated-<时间戳>`；指定的目录必须尚不存在且在源目录之外。

退出码 0 表示已观测规则没有硬失败且核心检查完整覆盖，可能仍有软性告警或非核心项未覆盖；不表示语义验收通过。1 表示硬失败、任一会话的核心检查覆盖不足，或产物不完整。

## 时间花在哪、怎么省

同一条会话的轮次只能串行：每轮依赖上一轮的历史，服务端也有会话级锁。时间几乎全花在主 Agent 作答上，平均每轮约 30 秒；加会话只多拿样本，不会更快。

- **稳态期提前停**：`run.steady-generations`（默认 3）。hold3 压出原文后再观测到这么多代就跳到末轮，给出两组相邻对比，每次省七八分钟。设成 0 跑完整本剧本。
- **前两段不减轮次**：压缩按字数触发，每代要攒 10～15 轮；业务规则要等标记轮被压出原文才生效。删铺垫轮只会让更多检查变成没观测到。
- **离线重放**：反复改压缩提示词时用。实跑每长出一代摘要，都会把发问前库里的上下文存成 `gen-K.input.json`。压缩只在一轮开头触发，那一刻的上下文就是这份快照加上这一问。重放用 agent 模块里的生产压缩器，按代串着重压：上一代摘要换成重放出来的那份，切点、素材渲染、模型和预算都走生产代码与 `application.yaml`，只有提示词读仓库文件。每代的素材字数必须和实跑一致，对不上就报错，不出结论。

离线重放有三个限制：

- 对话冻结在那次实跑，主 Agent 不会因为新摘要改变回答。所以弹卡、每轮是否正常结束、业务库写入这三项不判。
- 压缩时机沿用实跑。
- 要能连上模型：`application.yaml` 里 `agent.chat` 引用的密钥变量（默认 `DEEPSEEK_API_KEY`）必须在当前 shell 里。

定稿后仍要 PUT 上线再实跑一次。旧产物没有快照，不能重放。

## 剧本

`script.txt` 一行一问，问题文本不许重复。行首 `[ref]` 标出判定规则要用的轮次，分三段：

| 段 | 内容 | 关键标记 |
| --- | --- | --- |
| 一 | AirPods Pro 左耳无声：排查 → 查订单 → 放弃 Max → 申请先别提交 → iPad 预算颜色、先别下单、放弃 → 放弃 AirPods 4 | `diag` `hold1` `ipad_*` `a4_drop` `hold2` |
| 二 | 假设句、用户自称已有单号、明说放行（会弹卡并被拒）、又说先别提交 | `hypo` `claim` `release` `hold3` |
| 三 | 稳态：所有事项都已出现过，只反复问送修细节，看摘要还涨不涨 | `final` |

改剧本后，`CompactionChecks` 里依赖的标记都要还在，缺了会直接报错。

暂缓判定按用户是否已经明确要求办理区分：

- 从 `hold1` 到 `release` 之前（包括 `hypo`），用户仍在咨询，待办允许明确写“无”；空白或缺少待办小节不算“无”。若写了送修待办，每条都必须标明暂缓。
- `hold3` 之后，用户已经在 `release` 明确要求过提交，待办必须保留“提交申请——暂缓”，不能写“无”。
- 两个阶段都必须保留禁止提交的限制，都不允许残留当前放行说法或把暂缓事项放入下一步。放宽待办不豁免这些检查。

## 产物

- `facts.json`：被测压缩提示词的 md5 与字数、剧本 SHA-256、订单签收日期、开跑前已有的售后单、新增写入数。
- `script.txt`：新实跑保存的剧本快照；续跑时不得换剧本。
- `session-N/turns.jsonl`：每轮实际发送的 `question`、状态、工具、工具结果、被拒的卡、错误、回答。新运行的 `cardCalls` 保存确认卡的工具名、调用 ID 和原始参数；保留 `cardTools` 兼容旧产物。
- `session-N/gen-K.json` 与 `gen-K.md`：第 K 代摘要，以及它压到了第几轮原文。
- `session-N/gen-K.input.json`：长出第 K 代那一轮发问前的上下文快照，离线重放的素材。
- `时间戳-replay/`：离线重放的产物，结构同上；`facts.json` 里 `replayOf` 指向源产物，`gen-K.json` 多记实跑那代的字数。
- `report.md`：逐会话的失败项、覆盖情况与合并结论。FAIL/WARN 与覆盖不足可以同时存在。
- `metrics.json`：逐检查的观测数、失败数、连续失败段数、受影响代数、最长连续代数，以及 `unobserved`、`covered`、原因。`NO_WRITE` 只生成一条 `scope=global` 的运行级记录。
- `coverage.json`：每项检查完整覆盖的会话数与应观测会话数。PASS + UNCOVERED 不合并成 PASS；WARN/FAIL 也不能掩盖核心项缺覆盖。
- `observations.jsonl`：逐代规则判定与原因，供复核前后变化。主 Agent 行为记录的代号为 0，不代表压缩代。
- `evidence.json`：每条会话的原文恢复数量及证据路径。
- `evaluation.json`、`evaluator-source/`、`evaluated-script.txt`、`inputs-sha256.json`：本次判定器源码快照及 SHA-256、实际阈值、用于定位的剧本、输入文件哈希。重判使用本次记录的阈值，不冒充历史运行时配置。

“独立出现”按同一检查的连续失败段计数：连续错五代算一段、影响五代；通过一代后再次失败才另算一段。
这是摘要可观测的连续性指标，不证明模型没有在中间重新犯错，也不区分同一检查下同时发生的多个语义错误。
报告同时保留影响代数，不用段数下降代替内容验收。行为检查不适用这些按代统计的列。

判定器服务于本套固定剧本，并不是通用中文语义裁判：全部确认卡被拒，因此「已完成」必须为空，
「当前进度」也不能凭旧单号宣称本次提交成功。旧售后单类型与状态常量来自 `biz-data/05-after-sale.sql`；
该数据集修改后需要同步常量与自测。空会话产物直接判为无法下结论，不会返回通过。

## 结论口径

- `UNCOVERED` 不等于通过。核心检查只要在任一会话未覆盖，或者有应检查的代因缺少证据而跳过，就不能报整体通过。检查失败和覆盖不足独立展示。`NO_WRITE` 只需覆盖整次运行一次，不给第二条会话制造缺失。
- 一条会话只算一个样本。摘要有随机性，任一会话 FAIL 即 FAIL。
- 长度区间为 `[1, 2000]`：下限只拦空摘要，不因短于 300 字判失败；信息完整性由限制、排查、订单号等业务检查判断。2000 是本剧本的精简程度上限，与提示词中的 6000 字符要求分开。

## 引文证据与旧产物

只有在该代 `compactedThrough` 范围内的真实用户消息中找到出处，才从措辞检查里剥除引文。允许忽略标点和空白、以及用分号/省略号明示的摘录拼接；不允许删改词语。括号内位于“原话”之前的助手说明仍保留并检查。普通术语或工具错误信息被加引号，不因此成为用户原话；找不到用户出处时不会被剥除，只有显式标为用户原话的内容才接受 `QUOTE_SOURCE` 检查。

新产物使用轮次记录中的 `question`。旧产物从 `gen-K.input.json` 恢复实际 USER 消息，排除助手、工具以及 `__compaction_summary__`；只有快照问题和消息顺序与剧本轮次对齐才用于定位。当前剧本本身不能充当用户说过这句话的证据。未来轮次的原话不会用于较早代。重放可从 `replayOf` 的对应原会话恢复这些证据。

完整来源中找不到显式引文，记 FAIL；来源不完整且仍有未验证的引文，记 UNCOVERED，并保守跳过依赖引文剥除的检查。这会使少数旧 FAIL 变成证据不足，不表示内容已被证明正确，也不撤销原报告已保存的证据。真实但已失效的放行引文仍受暂缓规则检查，来源真实性不代表授权有效性。

放行轮新增 `RELEASE_TOOL` / `RELEASE_ORDER`：工具限 `submit_ticket`、`apply_after_sale`；前者核对工单 `content` 中完整订单编号，后者核对 `orderNo`。旧确认卡未保存参数时，订单检查记 UNCOVERED，不从助手回答猜测。这些只是主 Agent 响应的有限检查，不保证工具选择、售后类型等业务决策正确，也不验证授权经过摘要的继承。`CARD_ON_RELEASE` 仍为软性检查。

## 已知漏检与后续范围

订单号按完整数字编号匹配，避免将 `1882329`、`AS88232001` 当作 `88232`；出现正确编号仍不能证明事项归属正确。“称”仅识别用户称、客服称、对方称、电话称、声称，避免“名称”误命中；来源检查仍为启发式。

本轮不继续以正则追逐语义句式。以下反例仍可能通过对应规则，不能把 PASS 解释为这些关系已经正确：

- 左右耳颠倒、已做排查变成“尚未重置或配对”，仍可能通过 DIAGNOSIS。
- “预算至少 4000，只要金色，排除银色和深空灰”，仍可能通过 IPAD_CONDITIONS。
- “尚未放弃”、不同对象的暂缓/放行混在一行，可能绕过状态检查。
- “手续已经办妥”等未收录措辞可能绕过 NO_FAKE_DONE。
- “用户尚未表示同意办理”“不能据此认为已提交”等正确否定句仍可能误报。

完整语义验收需另建状态真值、压缩后续接任务和经过校准的判定方法。本轮只改进确定性规则、证据记录、覆盖报告及历史可追溯性。
