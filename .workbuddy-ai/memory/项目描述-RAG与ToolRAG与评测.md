## 一、RAG：四条通道怎么合，为什么这么设参数

### 简历可用文案

> **多通道检索与融合**
> 向量 / 关键词 / 图 / 联网四路并行召回，RRF 按名次融合后统一 Rerank。**RRF 的 k 设为 20 而非业界默认 60**——候选池实际只有 20~40 条，k=60 会把名次差异过度平滑，头部失去区分度；同时给四条通道配差异化权重（向量 1.0 / 关键词 1.0 / 图 0.8 / 联网 0.5），让补充通道不会因名次靠前压过主通道。
>
> **在融合后加了一道证据闸门**（精排分下限 0.2）：检索的固有问题是"库里没答案也照样返回最像的 N 条"，模型会拿这些凑数的段落硬答。闸门在整批最高精排分低于阈值时整批丢弃，让"检索不到"成为一个正常返回结果，而不是喂给模型一堆噪音。

### 面试深挖点（三个，都被追问过）

**① 为什么不用加权分数融合（Weighted Score），用 RRF？**

因为量纲不可比。向量分是余弦相似度（0~1 有上界），关键词分是 BM25（无上界，随长度和词频浮动）。直接加权要先归一化，而归一化方式本身就引入了主观性。RRF 只看名次不看分数，天然跨模态可比。

**代价**：丢了"分差信息"。第 1 名和第 2 名差 0.5 还是差 0.001，RRF 一视同仁。所以它适合"多通道、各自可信度接近"的场景，不适合"某一路明显更准"的场景。

**② 你说候选池只有 20~40 条，怎么确定的？**

这是配置的 `rerank-candidate-limit=40` 决定的——融合后按上限截断，只把前 40 个送进 Rerank。40 的来源是两件事的平衡：Rerank 的成本与延迟随条数线性增长；而 40 条已经能覆盖绝大多数正确答案的位置。

**这里有个真实的取舍**：截断是"弱势通道证据消失的第一现场"。某条通道召回的东西如果整体排在 40 名之外，它等于白跑了一趟。所以代码里专门在截断处打了并排日志（池内与出池分布），就是为了能看见"某通道被整体截没"。否则下游 Rerank 看到的输入已经是 0，你查不出是"没召回到"还是"召回到了但被截掉"。

**③ 证据闸门阈值 0.2 怎么定的？**

这个数字**跟 Reranker 模型强绑定**，换模型必须重测——不是普适常数。代码注释里写明了这一点（"随 reranker 而变，换模型看『检索归因 - 精排分布』重测"）。

同样的道理，`rag.feedback.bad-case` 里的词面重合阈值（0.15 / 0.25）也是**启发式线索**，不是判定标准。规则文案里明确写了"词面比较不能判定主题是否相关"——避免它被当成自动判决。

## 二、Tool RAG：工具规模与上下文解耦

### 先把三个真数字摆出来

```yaml
agent.mcp.tool-rag:
  enabled: true
  vector-enabled: true
  recall-top-k: 5          # 召回上限 5 个
  recall-min-score: 0.20   # 低于此分不召回
  semantic-weight: 0.65    # 语义占比
  keyword-weight: 0.35     # 关键词占比
```

打分公式（`ToolRagService`）：

```
score = (语义分 × 0.65 + 关键词分 × 0.35) / (0.65 + 0.35)
```

关键词分不是简单计数，**工具名和描述的权重差 4.3 倍**：

```java
return Math.min(1.0, (nameHits * 1.5 + descriptionHits * 0.35) / tokens.size());
```

**为什么差这么多**：工具名是规范化的「动词_对象」结构（`create_reminder`、`search_artist_events`），命中即强信号；描述里"查询""信息""返回"这类词每个工具都有，命中说明不了什么。

### 简历可用文案

> **工具召回层（Tool RAG）**
> 为「工具数量增长」与「上下文预算」解耦，设计了混合召回的 MCP 工具召回层：语义向量 + 关键词双路打分（0.65 / 0.35 加权），其中关键词部分对工具名给 1.5 权重、对描述给 0.35——工具名是规范化的动词+对象结构，命中即强信号，描述里的通用词则几乎无区分度。
>
> 三个工程约束是重点：
> - **中文分词不引库**：17 个停用词过滤 + 双字滑窗（Bigram）切分，零依赖、零索引，正则直接扫
> - **向量故障自动降级**：embedding 调用异常时降级为纯关键词召回，不中断请求（`vectorFallback` 标记会进日志）
> - **空召回只保留常驻工具**：召回为空时**不**回退到全量注册，否则每句无关消息都会变成一张 all-tools 菜单，反而违背减载初衷

### 面试深挖点

**① 现在只有 3 个工具，为什么要做召回？**

**这是最容易被问倒的问题，必须正面答，不能绕。**

诚实答案：

> 3 个工具时召回确实是零收益——它们大概率全部被召回，等于全量注入。这套东西不是为了现在的 3 个工具做的，是为了两个更实际的原因：
>
> 第一，代码里工具是动态发现的（MCP 服务端 `listTools()`），数量不受我控制。我在设计方案时的目标是"工具从 4 个涨到 40 个，代码不用改"。所以召回层是**架构预留**，用配置开关控制。
>
> 第二，我做的时候经历过 24 个工具的阶段（电商 13 + OA 8 + 通用 3），那时候全量注入确实挤占了上下文。后来业务收敛把工具删到 3 个，召回层我保留了——因为删代码是有成本的，而它的开关是关得掉的。

**② 3 个工具时，为什么不干脆关掉？**

因为开着也没坏处，而且有两个真实收益：

| 收益 | 机制 |
|---|---|
| 常驻工具（resident）跳过召回 | 高频工具直连，省掉打分开销 |
| 空召回保护 | 召回为空时不会退化成"注册所有工具" |

**但要承认**：3 个工具下 `topK=5` 会把候选全部召回，实际效果等于全量注入。**如果重来一次，这个规模我会先关掉它。**

**③ 你评估过其它方案吗？**

评估过三条，代码注释和设计文档里都留了痕迹：

| 方案 | 结论 |
|---|---|
| 全量注入 | 工具 < 10 个时最优，第一个往返不浪费 |
| **Tool RAG（当前）** | 工具 10~30 个时性价比最高 |
| 延迟加载（`defer_loading`） | **没做**——我的模型不支持该字段，且替代方案（CallTool 代理）要牺牲 API 层的 schema 强校验 |

**第 3 点要能展开**：真正省 token 的不是"搜工具"，是服务端把 schema 从上下文里摘掉只留名字。`CallTool` 代理能模拟，但 `arguments` 变成裸 JSON，类型错、缺必填、幻觉参数都不会在 API 层被拦。**所以"不做"是算过账的，不是不知道。**

## 三、bad case：18 条确定性规则 + 双重去重

### 规模与结构

| 项 | 数字 |
|---|---|
| 规则总数 | **18 条**（RAG 侧 R1–R10，Agent 侧 A1–A8） |
| 规则代码 | `BadCaseRules.java`，286 行 |
| 存储 | 2 张表：`t_bad_case`（案件）+ `t_bad_case_signal`（信号） |
| 置信度 | `HIGH` / `LOW` 两级 |
| 严重度 | `S1`~`S4` 四级 |
| 去重键 | `occurrence_key`（VARCHAR 160） |
| 入口限流 | 每日 500 条、单会话每小时 5 条 |

### 规则清单（真实阈值）

**RAG 侧（R1–R10）**

| 规则 | 触发条件 |
|---|---|
| R1 | 执行链路有 ERROR / FAILED 节点 |
| R2 | 消息被中断 |
| R3 | 请求被拒绝（限流） |
| R4 | 有检索节点但来源为空 |
| R5 | 问题与来源词面重合 **< 0.08** |
| R6 | 检索耗时 > 近 7 天 P95 |
| R7 | 回答与证据重合 **< 0.06** |
| R8 | 有来源但回答含拒答措辞 |
| R9 | 回答 ≥ 200 字但无结束标记（截断信号） |
| R10 | 改写结果与原问题重合 **< 0.1**（语义漂移） |

**Agent 侧（A1–A8）**

| 规则 | 触发条件 | 默认阈值 |
|---|---|---|
| A1 | 未调工具却给具体回答 | **默认关闭**（误报高） |
| A2 | 知识检索工具执行失败 | — |
| A3 | 检索结果与问题重合过低（召回跑偏） | **0.15** |
| A4 | 回答与资料重合过低（未依据作答） | **0.25** |
| A5 | 单次检索耗时超阈值 | **3000 ms** |
| A6 | 模型生成的 query 与问题漂移 | **0.1** |
| A7 | 轮次超限 / 同工具重复调用 | **6 轮 / 3 次** |
| A8 | 检索成功但内容为空 | — |

### 简历可用文案

> **确定性 bad case 检测体系**
> 不依赖 LLM 评判，用 18 条确定性规则从运行审计里抽取异常线索（RAG 侧 10 条 + Agent 侧 8 条），覆盖执行错误、召回跑偏、证据缺失、回答未依据资料、工具性能、轮次不收敛六类。
>
> 三个设计取舍：
> - **规则只给线索，不给判决**。每条规则的文案里都写明误报边界（例："词面比较不能判定主题是否相关，需人工核对"）。词面重合是廉价的异常探测器，不是语义判据——把它当判据会产出一堆假阳性。
> - **高危规则默认关闭**。A1（未调工具却作答）误报率最高，默认 `enable-no-tool-call-rule=false`。宁可漏检，不要让人每天处理一百条噪音后彻底不信这套系统。
> - **双层去重**。`occurrence_key` 做同源信号归并，入口再叠每日 500 条 / 单会话每小时 5 条限流，防止一个出问题的会话把池子刷满。

### 面试深挖点

**① 为什么不用 LLM 当裁判？**

因为**不可回归**。同一个 case 跑两次，LLM 可能给两个结论，那这套检测就没法用来做上线门禁——你无法判断"这次通过、上次不通过"是系统变好了还是裁判心情变了。

确定性规则的价值不在准，在**稳定**。我宁可规则少 10 条、阈值粗一点，也要保证同一个输入永远同一个输出。

**② 但确定性规则不懂语义，怎么处理？**

靠分工。规则负责**找可疑样本**（高召回、可接受低精度），LLM 负责**判断可疑样本**（人工触发、不进自动化链路）。

代码里有 `auto-review` 配置，默认 `enabled: false`——就是这个分工的体现。自动审核开了才有 LLM 参与，而且限了每日 100 条、输入 24000 字符、20 秒超时。

**③ 18 条规则的阈值怎么定的？**

**坦白说是经验值 + 校准，不是推导出来的。**

0.15 / 0.25 这两个重合阈值，是拿真实 case 试出来的：太低则满屏都是"疑似召回跑偏"，太高则真问题也报不出来。因为中文分词后重合率天然偏低（同一个概念换个说法词就重不上），所以阈值必须比英文场景低不少。

**我会主动说明这是启发式**——如果面试官追问"你怎么证明 0.15 是对的"，正确回答是"证明不了，它是可调的异常探测线，靠人工抽检校准"，而不是硬编一个理论依据。

## 四、评测：6 套回归 + 会拒绝出结论的报告器

### 规模

| 项 | 数字 |
|---|---|
| 回归集 | **6 套**：memory-evaluation、memory、memory-audit、long-term-memory、compaction、run-gate-audit |
| 断言类型 | **5 种**：`expectAll` / `expectAny` / `forbidAny` / `expectTools` / `forbidTools` |
| 数据集指纹 | SHA-256（`EvaluationDataset.fingerprint()`） |
| 现有 starline 数据集 | 3 个 case、7 轮对话 |
| 单轮超时 | 180 秒 |

### 断言设计（这是最能体现思考的地方）

```json
{
  "question": "薛之谦的生日是哪天？",
  "forbidTools": ["search_artist_events"]      // 负向断言：不该调
},
{
  "question": "那他有确定的演出安排吗？",
  "expectTools": ["search_artist_events"]      // 正向断言：该调
}
```

**同一个数据集里同时有正向和负向断言。** 只测"该调的时候调了"，会漏掉"不该调的时候也调了"——后者才是误调，用户感受更差（问生日却收到一堆演出信息）。

还有一类更细的：

```json
{
  "question": "回到最开始那个问题：我刚才问的是哪位艺人的演出？只回答艺人名，不要查资料。",
  "expectAll": ["薛之谦"],
  "forbidTools": ["search_artist_events"]      // 测记忆，同时禁止重新检索
}
```

**这条同时测两件事**：多轮记忆是否保持、以及模型会不会"偷懒重新查一遍"。

### 简历可用文案

> **Agent 回归评测体系**
> 六套独立回归集（记忆、上下文压缩、长短期记忆、运行闸门审计、综合评测），断言含正向（`expectTools`）与负向（`forbidTools`）两类——负向断言专门捕获误调，因为"该调没调"用户能感知，"不该调却调了"往往被忽略但体验更差。
>
> **报告生成器会拒绝出结论**：A/B 对比前强制校验 6 项一致性——运行状态必须 COMPLETE、不能含 FAILED 轮、计划/完成/实际轮键三者必须完全一致且顺序相同、数据集 sha256 指纹必须相同、对应轮 phase 必须相同。任一项不满足直接抛异常终止比较。
>
> 这个设计的出发点是：**「通过率 82% → 85%」这个数字，如果不是同一套条件跑出来的，就是假的。** 与其产出可疑结论，不如不出结论。

### 面试深挖点

**① 为什么要校验到"轮键顺序"这个粒度？**

因为多轮对话的**执行顺序**会影响结果。同样的题，先问 A 再问 B，和先问 B 再问 A，模型的上下文污染不同、记忆命中不同。只校验"题集相同"不够，顺序也必须一致。

**② 为什么要数据集指纹？**

防止"两组用的其实不是同一份数据"。这种错误极常见——你改了数据集的某一句话，以为只改了一句，但基线是用旧数据集跑的。sha256 一比就露。

**③ 这个评测和 bad case 什么关系？**

两者互补，不重叠：

| | bad case 检测 | 回归评测 |
|---|---|---|
| 输入 | 真实线上流量 | 人工构造的数据集 |
| 时机 | 持续运行 | 改动前后 |
| 目标 | 发现未知问题 | 防止已知能力退化 |
| 判据 | 确定性规则 | 断言 |

**一句话**：bad case 是"发现新毛病"，回归是"别把老毛病治回去"。少了任何一个都会有盲区。

## 五、⚠️ 一个必须先处理的问题

**你的工具现在只剩 3 个，Tool RAG 在这个规模下零收益。**

这意味着如果简历重点写 Tool RAG，面试官第一个问题就是"3 个工具为什么要召回"，而且这个问题**很难答得漂亮**。

三个处理选项：

| 选项 | 做法 | 风险 |
|---|---|---|
| **A. 合并写法（推荐）** | 把 Tool RAG 和 MCP 工具治理写成一节「工具注册与召回框架」，重点讲治理（权限闸门、读写声明、失败语义、身份隔离），召回作为其中一段 | 降低被单点追问的概率，且治理部分本身数据更硬 |
| B. 单列 Tool RAG | 独立成节，强调架构预留 | 被追问时较被动，但有准备话术也能过 |
| C. 不写 | 完全删掉 | 浪费了这块工程实践，且少一个"做过技术选型"的证据 |

**我倾向 A。** 理由：MCP 工具治理那部分（强制 `readOnlyHint`、异常不泄露 SQL、身份不进模型可控参数）每一条都能对上一个真实事故场景，比"召回框架"更抗追问。

## 六、面试前必须背熟的五个数字

如果只准备五个，选这五个：

| 数字 | 含义 | 为什么重要 |
|---|---|---|
| **k=20**（非默认 60） | RRF 平滑系数 | 证明你调过参、知道为什么调 |
| **0.65 / 0.35** | 语义/关键词权重 | 证明混合检索的比例是设计过的 |
| **1.5 vs 0.35**（4.3 倍） | 工具名 vs 描述的命中权重 | 证明你理解工具名是强信号 |
| **18 条** | bad case 规则数 | 证明体系的规模，不是拍脑袋写两条 |
| **6 项校验** | 报告拒绝出结论的条件数 | 证明评测的严谨度有具体落点 |

**这五个数字有一个共同点：都是"反直觉的选择 + 有理由"。** 面试官记不住二十个参数，但会记住"他把 k 从 60 调到 20 因为池子只有 40 条"这种细节。
