# 「已批未宣」场景改造方案：双维度模型 + 双通道架构

> 场景：用户问「薛之谦最近有什么演出」。很多场次在**文旅部门已批复**、但**大麦等票务平台尚未官宣上架**。这类信息在所有信源里是**最早、最权威**的，必须搜得出来，并准确表达它当前处在哪个阶段。
>
> 核查日期：2026-10-25。领域事实经文化和旅游部政务服务门户、陕西/天津/贵州/江西/四川等省级文旅厅公示页面实地核实。**本次未修改任何项目文件。**

---

## 0. 先纠正我此前设计的一个根本缺陷

我把「信源可信度」压成了一个字段：

```java
sourceType = OFFICIAL / UNVERIFIED      // 只看域名是否在票务平台白名单
saleStatus = PENDING / ON_SALE / SOLD_OUT / CLOSED / UNKNOWN
```

**这个设计在「已批未宣」场景下产生两类错误：**

| 错误 | 具体表现 |
|---|---|
| **权威信息被误判为不可信** | 文旅厅批复公示的域名是 `gov.cn`，不在票务白名单里 → 判为 `UNVERIFIED` → 模型只能说「网传有消息」。而这恰恰是**最权威**的信息 |
| **状态无处安放** | 批复已下但未开票，`saleStatus` 填什么？`PENDING` 暗示「待开票」，但实际连官宣都没有；`UNKNOWN` 又丢掉了「确定要办」这个最关键的信息 |

**根因：把两个正交的维度压成了一维。**

## 1. 领域事实（已核实，直接决定设计）

### 1.1 审批渠道的覆盖边界

| 演出类型 | 审批层级 | 公示渠道 | 可检索性 |
|---|---|---|---|
| **涉外 / 涉港澳台** | 省级文旅厅 | `zwfw.mct.gov.cn` 全国统一库 + 各省厅官网 | ✅ 有结构化统一入口 |
| **5000 人以上大型** | 县级初审 → 市级审查 → 省级复核 | 省级/市级公示 | ✅ 多数会进省级涉外库 |
| **纯内地中小型** | 区县级文旅局 | 各区县政府网站 | ⚠️ 极度分散，无统一入口 |

**一个反直觉的发现**：大型演唱会**几乎都走省级涉外审批**——因为乐队、舞美、技术团队常有外籍成员。核查中看到万妮达（厦门站）、孙燕姿（天津站）、许嵩（天津站）都在涉外审批公示里。

**结论**：`zwfw.mct.gov.cn` 的覆盖面比名字听起来大得多。**先做这一个源，就能覆盖大部分「已批未宣」的演唱会场景。**

### 1.2 全国库详情页的实际字段

实地抓取确认的 8 个字段：

```
演出名称： 专场演出
演出地：   上海市-上海市-上海市          ← 省-市-区三级
演出时间： 2025-07-03 至 2025-07-03     ← 起止日期
演出场所： 回响之地Music Park
报批单位： 莱音商务咨询（上海）有限公司
审批单位： 上海市文化和旅游局
批复时间： 2025-02-05
文号：     沪文旅许[2025]0390号
```

**注意时间差**：批复 2025-02-05 → 演出 2025-07-03，**提前 5 个月**。这就是「已批未宣」窗口期的真实长度。

### 1.3 省级公示的格式差异（说明为什么必须配置化）

| 省份 | 栏目名 | 特点 |
|---|---|---|
| 全国库 | 全国涉外营业性演出活动查询 | 结构化 8 字段，有统一 URL 结构 |
| 陕西 | 网办涉外、涉港澳台营业性演出行政许可情况公示 | 列表页含编号段（如 610000522026000296-323），正文是 HTML 表格 |
| 天津 | 审批公示 | 按周汇总，有「变更」类条目 |
| 贵州 | 行政审批公示 | 逐条「营业性演出准予许可决定」+ 文号 |
| 江西 | 双公示 | 逐条「营业性演出准予许可决定」+ 编号 |

**格式完全不统一**，不可能写一个通用解析器。这就是为什么省级源要**配置化 + 逐省适配**，并且**先只做全国库**。

## 2. 核心模型：两个正交维度

### 2.1 维度一：信源层级 `sourceTier`

表示「这条信息是谁说的」，决定它能承载多强的结论。

| 值 | 含义 | 权威性 | 能否作为结论 |
|---|---|---|---|
| `GOV` | 政府审批公示 | **最高**（法定程序） | ✅ 可说「已获批复」 |
| `PROMOTER` | 主办方 / 场馆 / 艺人工作室 | 高（官方宣布） | ✅ 可说「官方已宣布」 |
| `TICKETING` | 票务平台 | 高（可交易） | ✅ 可说「已开票」 |
| `MEDIA` | 新闻媒体 / 自媒体 | 低 | ❌ 只能说「网传」「有消息称」 |

### 2.2 维度二：演出阶段 `stage`

表示「这个演出现在走到哪一步」。

| 值 | 含义 | 关键特征 |
|---|---|---|
| `APPROVED` | 已获批复，未官宣 | 有演出日期和场馆，**无开票时间** |
| `ANNOUNCED` | 已官宣，未开票 | 有明确活动名，可能已有开票预告 |
| `ON_SALE` | 已开票 | 有开票时间，票务页面可访问 |
| `SOLD_OUT` | 售罄 | 页面显示无票 |
| `ENDED` | 已结束 | 演出日期已过 |
| `CANCELLED` | 已取消/延期 | 公示有变更记录，或人工标记 |
| `UNKNOWN` | 无法判断 | 信息残缺 |

### 2.3 为什么必须拆开（矩阵）

| | APPROVED | ANNOUNCED | ON_SALE | ENDED |
|---|---|---|---|---|
| **GOV** | **★ 已批未宣**（本需求核心） | 有 | 少见 | — |
| **PROMOTER** | 罕见 | **★ 官宣** | 有 | — |
| **TICKETING** | 不存在 | 待开票 | **★ 可购票** | 有 |
| **MEDIA** | 传闻 | 网传 | 转载 | 回顾 |

**`GOV + APPROVED` 和 `TICKETING + ON_SALE` 都是可信的，但含义完全不同。**

前者意思是「确定要办，但你还买不到票，开票时间也未定」；后者意思是「现在就能买」。如果只有一个 `OFFICIAL` 字段，模型无法区分，只能说一句含糊的「有大麦的信息」。

## 3. 双通道架构

### 3.1 关键判断：审批数据入库，票务数据检索

我此前推翻「建表方案」，是因为**票务数据**量大、变化快、无 API。但**审批数据特征完全相反**：

| 维度 | 票务数据 | 审批数据 |
|---|---|---|
| 数据量 | 海量（每场多平台多票档） | **小**（全国每天几十条涉外演出） |
| 更新频率 | 分钟级（余票、加场） | **日更**（公示后基本不变） |
| 结构化 | 差（每平台页面结构不同） | **好**（8 个固定字段） |
| 可抓性 | 无 API、有反爬 | 公示页静态，可抓 |
| 时效价值 | 必须实时 | **延迟一天无影响** |

**所以：审批入库（保证「已批未宣」可靠可查），票务检索（保证开票信息实时）。**

这不是回到旧方案，而是**按数据特征分别处理**——审批数据值得建表，票务数据不值得。

### 3.2 数据流

```
通道一：审批入库（异步）
  定时任务（日更 03:00）
    → 抓 zwfw.mct.gov.cn 列表 + 详情
    → 解析 8 字段 → 落 t_starline_approval
    → content_hash 去重（公示页重复抓不出重复行）

通道二：票务检索（实时）
  search_artist_events 被调用时
    → WebSearchClient 搜「艺人 + 演唱会 + 开票」
    → 按域名打 sourceTier 标签
    → 文本抽取 stage

合并（工具内部）
  → 审批记录（本地库，GOV/APPROVED）
  → 检索结果（TICKETING/MEDIA）
  → 按「艺人 + 城市 + 日期±1天」合并为同一场
  → stage 取最靠后的，sources 保留全部
  → 输出
```

### 3.3 合并去重算法

同一场演出在两个通道可能都有：

```
审批记录：event_name="XX「天外来物」巡回演唱会-上海站", event_date=2026-12-20, venue="梅赛德斯"
票务结果：title="XX天外来物巡回演唱会 上海站",        eventDate=2026-12-20
```

合并键：

```java
mergeKey = normalizeCity(city) + "|" + eventDate + "|" + artistKey
// artistKey 用用户输入的艺人名，不做 NER
// 日期允许 ±1 天容差（跨零点场次的写法差异）
```

合并后：

- `stage` 取**最靠后的**：`ON_SALE` 覆盖 `APPROVED`
- `sources[]` **保留全部**，这样模型既知道「早就批了」也知道「现在能买了」
- 新增 `earliestSignalAt` = 最早的批复日期 → 能回答「这个演出多久前就有信了」

### 4.3 关键设计：不做艺人姓名抽取

**问题**：「永恒的海豚音2.0旗舰版·VITAS维塔斯2025巡回演唱会-上海站」里，艺人名是「VITAS维塔斯」。自动抽取需要 NER，且艺名千变万化（万妮达/VAVA、薛之谦/小薛）。

**简化方案**：**不抽姓名，查询时反向匹配**。

```sql
-- 用户查「薛之谦」，直接匹配活动名
SELECT * FROM t_starline_approval
WHERE deleted = 0 AND cancelled = 0
  AND event_name ILIKE '%' || ? || '%'
  AND event_date_from BETWEEN ? AND ?
ORDER BY event_date_from;
```

**为什么这样更可靠**：
- 公示的活动名里**必然包含艺人名**（这是报批要求）
- 用户已经提供了艺人名，不需要反推
- 避免 NER 错误带来的漏检

**唯一的补充需求**：艺名别名。用户说「小薛」时匹配不到 `薛之谦`。用两种方式解决，不需要建表：
1. 工具 description 教模型「用户说昵称时传正式艺人名」
2. 在 `t_starline_platform_source.crawl_config` 之外，另建一个轻量别名映射配置（properties 文件即可，不需要表）

### 5.2 全国库实现骨架

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class MctNationalApprovalCollector implements ApprovalCollector {

    private static final String DOMAIN = "zwfw.mct.gov.cn";
    private static final String LIST_URL =
            "https://zwfw.mct.gov.cn/wycx/qgswyyxychd/qgswyyxychdjg/";
    /** 礼貌抓取：单站点并发 1，请求间隔 2 秒 */
    private static final long REQUEST_INTERVAL_MS = 2000;
    private static final int MAX_PAGES_PER_RUN = 20;

    private final HttpClient httpClient = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(10))
            .followRedirects(HttpClient.Redirect.NORMAL)
            .build();

    @Override
    public String sourceDomain() {
        return DOMAIN;
    }

    @Override
    public List<ApprovalRecord> collect(LocalDate since) {
        List<ApprovalRecord> records = new ArrayList<>();
        for (int page = 1; page <= MAX_PAGES_PER_RUN; page++) {
            String html = fetch(LIST_URL + "?pageNo=" + page);
            List<String> detailUrls = parseDetailUrls(html);
            if (detailUrls.isEmpty()) {
                break;
            }
            boolean anyNew = false;
            for (String url : detailUrls) {
                ApprovalRecord record = parseDetail(fetch(url), url);
                if (record == null) {
                    continue;
                }
                // 批复时间早于 since 且已入库的跳过，由 content_hash 兜底幂等
                records.add(record);
                anyNew = true;
                sleep(REQUEST_INTERVAL_MS);
            }
            if (!anyNew) {
                break;
            }
            sleep(REQUEST_INTERVAL_MS);
        }
        return records;
    }

    /**
     * 详情页解析：8 个字段以「字段名： 值」形式逐行排列
     * <p>
     * 只依赖字段名定位，不依赖 DOM 结构——政府网站改版频繁，
     * 结构一改选择器就失效，而字段名相对稳定
     */
    private ApprovalRecord parseDetail(String html, String url) {
        String text = HtmlUtil.cleanHtmlTag(html);      // hutool，去标签留文本
        String eventName = extract(text, "演出名称");
        if (StrUtil.isBlank(eventName)) {
            return null;                                 // 不是详情页
        }
        String regionRaw = extract(text, "演出地");
        String timeRaw = extract(text, "演出时间");
        LocalDate[] range = parseDateRange(timeRaw);
        return new ApprovalRecord(
                eventName,
                regionRaw,
                range[0], range[1],
                timeRaw,
                extract(text, "演出场所"),
                extract(text, "报批单位"),
                extract(text, "审批单位"),
                extract(text, "文号"),
                parseDate(extract(text, "批复时间")),
                url,
                html,
                resolveApprovalLevel(extract(text, "审批单位")),
                "FOREIGN_HMT");                          // 该库只含涉外/涉港澳台
    }

    /** 「上海市-上海市-上海市」→ 省/市/区 */
    private String[] splitRegion(String raw) { ... }

    /** 「2025-07-03 至 2025-07-03」→ [from, to] */
    private LocalDate[] parseDateRange(String raw) { ... }

    /** 「上海市文化和旅游局」→ PROVINCIAL；「文化和旅游部」→ NATIONAL */
    private String resolveApprovalLevel(String approver) {
        if (approver == null) {
            return "PROVINCIAL";
        }
        if (approver.contains("文化和旅游部")) {
            return "NATIONAL";
        }
        return approver.contains("市") && !approver.contains("省") ? "MUNICIPAL" : "PROVINCIAL";
    }

    private String extract(String text, String field) {
        // 「演出名称: xxx」或「演出名称： xxx」
        Matcher m = Pattern.compile(field + "[:：]\\s*([^\\n]+)").matcher(text);
        return m.find() ? m.group(1).trim() : null;
    }
}
```

**⚠️ 实施时必须先做的一件事**：把列表页和详情页的真 HTML 各存一份到 `src/test/resources/`，用真实样本写解析测试。政府网站的 HTML 结构与文本渲染差异很大，**不能凭 `HtmlUtil.cleanHtmlTag` 就假定能拿到「字段名：值」格式**。

### 5.3 调度器

```java
@Slf4j
@Component
@RequiredArgsConstructor
@ConditionalOnProperty(prefix = "starline.approval", name = "enabled", havingValue = "true")
public class ApprovalSyncScheduler {

    private final List<ApprovalCollector> collectors;
    private final ApprovalRepository repository;

    /**
     * 日更即可：公示一旦发布内容基本不变，抓得太勤是浪费对方带宽
     * 凌晨 3 点避开工作时间
     */
    @Scheduled(cron = "${starline.approval.cron:0 0 3 * * ?}")
    public void sync() {
        LocalDate since = LocalDate.now().minusDays(7);   // 回看 7 天，接住补发和变更
        for (ApprovalCollector collector : collectors) {
            try {
                List<ApprovalRecord> records = collector.collect(since);
                int inserted = repository.upsert(collector.sourceDomain(), records);
                log.info("审批公示同步完成, source={}, fetched={}, inserted={}",
                        collector.sourceDomain(), records.size(), inserted);
            } catch (Exception e) {
                // 单个源失败不影响其他源，下一轮重试
                log.error("审批公示同步失败, source={}", collector.sourceDomain(), e);
            }
        }
    }
}
```

### 5.4 抓取的礼貌与合规

| 事项 | 做法 |
|---|---|
| 频率 | 日更一次，回看 7 天 |
| 并发 | 单源串行，请求间隔 2 秒 |
| User-Agent | 声明来源，如 `StarlineAgent/0.1 (event approval monitor)` |
| robots.txt | 实施前检查目标站点；不允许则不抓 |

### 6.2 合并器

```java
public final class EventMerger {

    /**
     * 同一场演出可能同时有审批记录和票务页面，合并为一条
     * <p>
     * 合并键：艺人 + 城市 + 日期（±1 天容差）
     * stage 取最靠后的，sources 保留全部
     */
    static List<EventItem> merge(List<EventItem> approved, List<EventItem> searched) {
        Map<String, EventItem> byKey = new LinkedHashMap<>();

        // 先放审批记录：它是「最早信号」，作为合并的基底
        for (EventItem item : approved) {
            byKey.put(keyOf(item), item);
        }

        // 再叠检索结果：同键则合并，否则新增
        for (EventItem item : searched) {
            String key = findMatchingKey(byKey, item);   // ±1 天容差匹配
            if (key == null) {
                byKey.put(keyOf(item), item);
            } else {
                byKey.put(key, mergeTwo(byKey.get(key), item));
            }
        }

        return byKey.values().stream()
                .sorted(Comparator
                        .comparing((EventItem i) -> phaseRank(i.stage()))
                        .thenComparing(EventItem::eventDate, Comparator.nullsLast(Comparator.naturalOrder())))
                .toList();
    }

    /** 审批是基底，票务/媒体验证或推进阶段 */
    private static EventItem mergeTwo(EventItem base, EventItem update) {
        return base.toBuilder()
                // 阶段只前进不后退
                .stage(laterStage(base.stage(), update.stage()))
                // 票务信息更准，用它覆盖空的
                .saleStartTime(StrUtil.isNotBlank(update.saleStartTime())
                        ? update.saleStartTime() : base.saleStartTime())
                .venue(StrUtil.isNotBlank(base.venue()) ? base.venue() : update.venue())
                // 信源全留
                .sources(concatDistinct(base.sources(), update.sources()))
                // 最早信号时间 = 两者中更早的
                .earliestSignalAt(earlier(base.earliestSignalAt(), update.earliestSignalAt()))
                .build();
    }

    /** APPROVED < ANNOUNCED < ON_SALE，取靠后的；CANCELLED 优先级最高（一旦取消就定论） */
    private static String laterStage(String a, String b) {
        if ("CANCELLED".equals(a) || "CANCELLED".equals(b)) {
            return "CANCELLED";
        }
        return stageRank(a) >= stageRank(b) ? a : b;
    }
}
```

## 8. 提醒功能的产品决策（关键）

用户在 `APPROVED` 阶段想设提醒，怎么办？这是本需求带来的**新问题**。

### 8.1 三种方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| a. 不允许设 | 要求必须已开票 | 简单 | **违背用户最核心的诉求**——他就是想提前蹲开票 |
| b. 按演出日期提醒 | 「演出前 7 天提醒我」 | 简单，可立即做 | 对抢票无用（那时期票早卖完了） |
| c. 开票监控 | 系统轮询，一旦发现开票立即提醒 | **直击痛点** | 需要轮询机制 |

### 8.2 推荐：b + c 组合，分两期

**第一期（b）：允许基于 APPROVED 记录创建提醒**

`t_starline_event_reminder` 现有字段已支持（`ticket_time` 可空），需要新增：

```sql
ALTER TABLE t_starline_event_reminder
    ADD COLUMN IF NOT EXISTS reminder_type VARCHAR(24) NOT NULL DEFAULT 'TICKET_TIME'
        CHECK (reminder_type IN ('TICKET_TIME','EVENT_DATE','ON_SALE_WATCH')),
    ADD COLUMN IF NOT EXISTS approval_id VARCHAR(64),
    ADD COLUMN IF NOT EXISTS artist_name VARCHAR(160);   -- 已有

COMMENT ON COLUMN t_starline_event_reminder.reminder_type IS
    'TICKET_TIME=开票前提醒 / EVENT_DATE=演出前提醒 / ON_SALE_WATCH=开票即提醒';
```

约束调整：

| 阶段 | 允许的 reminder_type | 提醒依据 |
|---|---|---|
| `ON_SALE` | `TICKET_TIME`（默认）、`EVENT_DATE` | 开票时间已知 |
| `ANNOUNCED` | `EVENT_DATE`、`ON_SALE_WATCH` | 开票时间可能已知 |
| `APPROVED` | **只能** `EVENT_DATE` 或 `ON_SALE_WATCH` | **绝不能** 设 `TICKET_TIME`（没有开票时间） |

**关键校验**（写进 `StarlineEventService.create`）：

```java
if ("TICKET_TIME".equals(reminderType) && StrUtil.isBlank(request.getTicketTime())) {
    throw new ClientException("该场次尚未公布开票时间，只能设置「演出前提醒」或「开票即提醒」");
}
if ("APPROVED".equals(stage) && "TICKET_TIME".equals(reminderType)) {
    throw new ClientException("该场次仅有审批信息，尚无开票时间，无法设置开票提醒");
}
```

这是**新增的业务规则违例**，正好对应 bad case 方案里的 `STARLINE_RULE_VIOLATION` 入口——如果 Agent 明知没有开票时间还去设 `TICKET_TIME`，就是一条高置信业务规则违例。

**第二期（c）：开票监控**

```java
/**
 * 开票监控：对 ON_SALE_WATCH 类型的提醒，定时检查对应场次是否已进入 ON_SALE
 * <p>
 * 频率取 30 分钟：开票信息不是秒级变化的，太频繁对票务站点不礼貌
 */
@Scheduled(fixedDelayString = "${starline.reminder.watch-interval-ms:1800000}")
public void checkOnSaleWatch() {
    for (var reminder : service.findOnSaleWatch()) {
        if (isNowOnSale(reminder)) {
            sendImmediateAlert(reminder);      // 立即发一封"已开票"提醒
            service.mark(reminder.getId(), "SENT", now);
        }
    }
}
```

**这个功能是产品差异化的核心**——竞品都在做「开票后提醒」，而这个能「一开票就提醒」，因为它的信号来源是审批库 + 票务检索双通道。

## 9. 与既有设计的关系

### 9.1 与 bad case 体系的衔接

新增两条可检测的业务规则违例：

| 规则 | 检测点 | 置信度 |
|---|---|---|
| `REMINDER_WITHOUT_TICKET_TIME` | Agent 在 APPROVED 阶段设 `TICKET_TIME` 提醒 | 高（确定性违反） |
| `STAGE_OVERCLAIM` | 回答把 `canBuyTicket=false` 说成「可以买票」 | 中（需人工确认措辞） |

前者可走 `STARLINE_BUSINESS / STARLINE_RULE_VIOLATION` 高置信入口；后者走行为信号 + 自动评审。

### 9.2 与信源治理的关系

`t_starline_platform_source` 的双评审（PRODUCT + ENGINEERING）正好用来治理新增的 GOV 源：

- **PRODUCT 评审**：这个公示渠道对公司业务是否可用、内容是否覆盖我们需要的信息
- **ENGINEERING 评审**：抓取是否合法、字段是否稳定、解析是否可维护

**每个省级源上线前都必须过这两道评审**——这正是该表设计的初衷，不需要新造机制。

### 9.3 与我此前方案的差异（需要更新的地方）

| 原方案 | 新方案 | 原因 |
|---|---|---|
| `sourceType`: OFFICIAL/UNVERIFIED | `sourceTier`: GOV/PROMOTER/TICKETING/MEDIA | 二档无法表达「政府比票务平台更权威」 |
| `saleStatus`: PENDING/ON_SALE/... | `stage`: APPROVED/ANNOUNCED/ON_SALE/... | 原字段混了「阶段」和「能否买票」 |
| 纯检索，不建表 | 审批入库 + 票务检索双通道 | 审批数据量小、稳定、结构化，值得建表 |
| 白名单只有票务域名 | 白名单分层，含 gov 域名 | 政府公示必须被识别为最高权威 |
| 提醒只能基于开票时间 | 三种提醒类型，APPROVED 阶段可用 | 否则用户没法蹲开票 |

## 12. 风险与边界

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| 1 | **覆盖不完整** | 纯内地中小型演出在区县级公示，本方案覆盖不到 | 如实告知「未查到审批信息不代表没有演出」；不承诺全覆盖 |
| 2 | **批复后仍可能取消** | 票房、档期、政策原因 | 措辞一律「已获批复」不写「确定举办」；维护 `cancelled` 标记 |
| 3 | **政府网站改版** | 字段名相对稳定但结构会变 | 按字段名定位而非 DOM 选择器；解析失败告警而非静默 |
| 4 | **抓取合规** | 政府网站可能禁止自动化访问 | 日更低频、声明 UA、先查 robots.txt；不允许则退化为搜索引擎检索 |
| 5 | **活动名不含艺人本名** | 如「永恒的海豚音2.0旗舰版·VITAS维塔斯」 | 用户输入的艺人名做 `ILIKE` 匹配；补充别名配置 |
| 6 | **同场次名称差异大** | 审批叫「XX巡回演唱会-上海站」，票务叫「XX天外来物 上海」 | 合并键用「城市+日期±1天」，不依赖名称相似度 |
| 7 | **公示滞后** | 批复到公示可能隔几天 | 无法解决，属于法定流程时间；回看 7 天接住延迟 |
| 8 | **省级源工作量爆炸** | 31 个省格式各异 | 只做全国库（覆盖大部分大型演出）；省级源按需逐个加，每加一个走双评审 |
| 9 | **审批信息被误当"已开票"** | 模型措辞出错 | `canBuyTicket` 布尔硬约束 + `stageLabel` 现成中文标签 + system prompt 措辞表 |
| 10 | **提醒在 APPROVED 阶段无意义** | 按演出日期提醒对抢票无用 | 提供 `ON_SALE_WATCH` 类型；第二期实现轮询 |

---

## 13. 一句话总结

> **「已批未宣」不是搜索覆盖问题，是信息模型问题。**
>
> 必须承认演出信息有两个正交维度——**谁说的**（信源层级）和**走到哪一步**（演出阶段）。压成一个字段，就会出现「最权威的信息被当成网传」和「已批未宣无处安放」。
>
> 承认之后，架构自然分成两条通道：**审批数据入库（量小稳定，保证已批未宣可查）+ 票务数据检索（量大易变，保证开票信息实时）**，在工具内合并。这不是回到旧方案，而是按数据特征分别处理。
