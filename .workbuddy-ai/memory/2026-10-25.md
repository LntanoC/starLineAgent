## bad case 判定规则全量核对（只读，基于 `BadCaseRules.java` + `BadCaseService.java` + `BadCaseRepository.java`）

### 关键结论：入口与规则是两层，不要混淆

- **入口（什么会被建单）：目前只有一个——用户点踩。**
  `BadCaseRepository.pendingFeedback` 的 SQL 是
  `WHERE f.vote=-1 AND f.deleted=0 AND (时间窗口) AND NOT EXISTS(t_bad_case 中同 message_id+user_id)`
  → **没被点踩的消息永远不会成为 bad case**，无论链路里报了多少错。
  `BadCaseScanJob` 只是定时把「已点踩但未建单」的 feedback 捞出来分析（5 分钟一次增量 lookback 60min，1 小时一次全量补扫）。

- R1 任一 trace 节点 status=ERROR/FAILED
- R2 `message_status`=INTERRUPTED（用户取消/超时）
- R9 status=NORMAL 且 answer≥200 字 且末尾无 `[。！？.!?…）)】\]」”"：:；;]` 且不以 ``` 结尾 → 截断弱信号

### 设计意图（代码文字已明示）
每条规则文案均带「疑似…需人工核对」「词面比较不能判定语义/幻觉」；无命中时兜底文案是「未命中可用线索…**这不代表回答正确**」。→ 规则只负责**提出怀疑**，`root_cause`（7 分类：RETRIEVAL_MISS/RETRIEVAL_NOISE/INTENT/HALLUCINATION/FORMAT/PERF/OTHER）由人填，`fix_action` 6 分类（MAPPING/INTENT_NODE/KNOWLEDGE_BASE/PROMPT/RERANK/NONE），状态机 PENDING/REVIEWED/IGNORED/FIXED。

- **四层下沉判定**（本设计核心）：① 实体相关性过滤（丢「同款/翻唱/壁纸」噪音）② 来源域名白名单两档 `OFFICIAL/UNVERIFIED` ③ 时效 `publish_time + 7天阈值`（**不是** v1 的 6 小时——那是自己核验时间的阈值，网页发布时间用 6 小时会全标过期）④ 售票状态文本抽取，`UNKNOWN` 是正常高频值。
- **工具边界**：`total=0` 必须给 `notes`（防编造）；`UNVERIFIED` 不得作为创建提醒依据；查询与建提醒严格分离；不做「查不到自动转 youcom_search」（会让模型拿到未下沉的原始结果自己判断）。
- 白名单**只用于事后打标，不用于检索过滤**（否则「官方未公告但媒体已报道」查不到）。
- 检索源选型：主用腾讯云元宝搜索（原生 `Site`/`Freshness`/发布时间/站点名），`youcom_search` 兜底；建议抽 `WebSearchClient` 接口两实现可切换。
- 依赖 `current_date`：用户说「最近/今年」时必须先调它确认当前日期，否则模型按训练数据猜日期必然错。
- 意图节点 `kind=2 + mcp_tool_id=search_artist_events`，examples 覆盖五类问法（标准/时间/城市/别名/售票状态）。

同时确认了项目 MCP 工具全量清单：**24 个 = bit 电商 13（6读7写）+ enterprise OA 8（5读3写）+ common 通用 3（全只读）**，其中 **starline 自己的业务域 0 个工具**。

### 补充：`current_date` 与「最近」的时间语义

- `current_date` 只返回 `LocalDate`（无时刻），入参 `timezone` 默认 `Asia/Shanghai`，注入 `Clock` 便于测试固定时间。它是相对日期的唯一基准——模型没有时钟，只能靠训练数据猜今天，所以票务类工具必须在 description 里强制「先调 current_date」。
- **「最近」有三重歧义**：方向（即将到来 vs 刚结束）、窗口长度（周/月/季/年）、参照点（今天 00:00 / 发消息时刻）。结论是**不定义，而是显式化 + 可修正**。
- **默认双向窗口：过去 30 天 + 未来 90 天**。90 天依据演出行业「提前官宣」特征（官宣到开票 1-4 周、开票到演出 1-2 月、大巡演提前 3-6 月）；7 天会漏掉已开票未演的抢票窗口，一年又带回过期/取消信息。30 天过去是为了能说「刚错过」而不只是「查不到」。
- **`freshness` 三个取值全部双向**：`week`=前7+后30、`month`=前30+后90（默认）、`year`=前90+后365。不提供「只往后看」选项。
- **绝不让模型把「最近」翻译成日期传 `dateFrom/dateTo`**：跨月/跨年/闰年易错，更麻烦的是行为不可复现，导致 bad case 分析与回归评测无法定位。区间一律服务端展开。
- 返回加 `searchedRange {from,to}` + `items[].relativePhase`（`UPCOMING/ONGOING/PAST/TBD`）——把假设摊开，用户觉得不对可说「再往后看看」。类比：出租车司机说「前面路口大概 500 米，行吗」。

### 意图树与 MCP 工具注册的关系（代码核实，三个非直觉结论）

意图树 `t_intent_node` 实际承担**两个互不相干的职责**，走两条独立代码路径：

1. **KB/SYSTEM 节点** → 参与意图分类（`DefaultIntentClassifier.classifyTargets`）+ 决定检索范围（`collectionNames`）。
2. **MCP 节点（kind=2）** → **只做工具注册/授权，完全不做意图分类**。

三个容易踩错的点：

- **MCP 节点不参与意图打分**：`classifyTargets` 的候选过滤是 `.filter(node -> node.isKB() || (WORKFLOW && node.isSystem()))`，**MCP 节点被排除在外**。所以「意图树 MCP 节点」这个名字有误导性——它不是「识别用户想调哪个工具」的地方，模型是靠工具 description 自己选工具的（ReAct 机制）。
- **MCP 节点必须是叶子节点**：`listMcpToolNodes()` 从 `leafNodes` 里筛。给 MCP 节点挂 children 会让它变成非叶子，工具直接消失。
- **MCP 节点的 `examples` 当前完全没用**：`buildPrompt()` 只遍历 KB 候选拼提示词，AgentToolCatalog 也不读 examples。examples 只对 KB/SYSTEM 节点有效。而 `description` 是**有用的**——`McpToolBinding.of()` 优先用意图树 description 覆盖服务端 description（运营可不改代码改工具描述）。

**为什么要取交集（能力 ∩ 授权）**：
- mcp-server 是「我有什么能力」，意图树是「这个业务场景允许用哪些」→ 交集才是实际暴露给模型的工具集。
- 部署解耦容错：server 没启动/版本旧/工具改名时，交集自动缩水，只记 `unavailableToolIds` 告警，不会让 Agent 启动失败。
- 防撞名：`RESERVED_TOOL_NAMES`（`search_knowledge`/`memory_flush`/`skill_load`）保护内置工具不被 MCP 覆盖，因为 Toolkit 按名注册会静默覆盖。
- DB 层还有 `CREATE UNIQUE INDEX uk_intent_node_mcp_tool ON t_intent_node (mcp_tool_id) WHERE kind = 2 AND deleted = 0`——一个工具只能挂一个节点。

**⚠️ 重大运维坑（已修正 v2 文档的 SQL 用法）**：意图树缓存在 Redis（`starlineagent:intent:tree`，**TTL 7 天**），只有 `IntentTreeServiceImpl` 的增删改会调 `clearIntentTreeCache()`。**直接跑 SQL INSERT 绕过了 Service，缓存不清 → 工具最长 7 天不生效、且无任何报错**。必须手动 `redis-cli DEL "starlineagent:intent:tree"`。清完后 `ReActAgentProvider` 的 fingerprint 比对会触发 Agent 重建，不用重启应用。

**星序意图树设计稿**（已给出完整 SQL）：`STARLINE`(域) → `ARTIST_EVENT_QUERY`(MCP叶子,search_artist_events,免确认) / `REMINDER`(分组,非叶子) → 下挂 `REMINDER_CREATE`(写,需确认)/`REMINDER_QUERY`(读)/`REMINDER_CANCEL`(写) / `SOURCE_REGISTRY`(KB叶子,collection_names=starline_source_registry)。

## 【重大修正】「已批未宣」场景：双维度模型 + 双通道架构

用户指出关键领域事实：**很多场次文旅部门已批复但票务平台未官宣**，这类必须搜出来。核查后确认我此前设计有根本缺陷。

**领域事实（实地核实）**：
- `zwfw.mct.gov.cn/wycx/qgswyyxychd/` 「全国涉外营业性演出活动查询」**只覆盖涉外/涉港澳台**（省级文旅厅审批），内地中小型演出走区县级审批、不在此库。
- 但**大型演唱会几乎都走省级涉外审批**（乐队/舞美/技术团队常有外籍成员）。核查中看到万妮达（厦门）、孙燕姿（天津）、许嵩（天津）都在涉外库中。→ **先做这一个源就能覆盖大部分场景**。
- 详情页 8 个固定字段：演出名称 / 演出地(省-市-区) / 演出时间(起止) / 演出场所 / 报批单位 / 审批单位 / 批复时间 / 文号。
- **批复到演出可提前 5 个月**（如批复 2025-02-05、演出 2025-07-03）→ 这就是「已批未宣」窗口期真实长度。
- 省级公示格式完全不同（陕西/天津/贵州/江西各不相同），无法通用解析。

**核心修正：两个正交维度必须拆开**
- 原设计 `sourceType = OFFICIAL/UNVERIFIED`（只看票务域名白名单）→ 政府公示被误判 UNVERIFIED
- 原设计 `saleStatus` 混了「阶段」和「能否买票」→ 已批未宣无处安放

## MCP 工具注册的最佳实践（维护成本问题）

用户提出核心痛点：意图树 MCP 节点手工维护繁琐，Agent 拓展时节点不会自动变多。

**关键澄清**：Agent 模式下意图树 MCP 节点的唯一职责是「工具注册白名单」，不参与工具选择。`AgentToolCatalog.resolveMcpTools()` 只有这一个工具来源，没有第二条路——**mcp-server 写了工具 ≠ 模型能看到**。

**取交集之外还必须做的四件事**：① description 覆盖（意图树优先）② displayName ② require_confirm ④ **清 Redis `starlineagent:intent:tree`（TTL 7 天，不清则最长 7 天不生效且无报错）**。

**重要发现削弱了白名单必要性**：`needsConfirm = 意图树勾选 || !readOnlyHint`，即使意图树漏配，写工具也会因服务端 `WRITE` 标记自动要求确认（`McpServerConfig.requireReadOnlyHint()` 启动强制校验）。→ 意图树的不可替代价值只剩「覆盖 description」和「排除不想暴露的工具」两条。

**三阶段演进（推荐）**：
- **阶段一（现在够用）**：删完 bit/enterprise 后只剩 4 个工具一个域，手工插 4 个节点 + weather 设 enabled=0 + 清一次 Redis，10 分钟搞定。
- **阶段二（工具 >6 个时）**：加 `McpIntentNodeSynchronizer` 自动发现。需先给 `AgentMcpClients` 加 `discoveredToolIds()` / `remote(toolId)` 只读出口（当前 `tools` 是 private）。四种策略：`OFF` / `DISCOVER_ONLY`（只告警漏配，推荐默认）/ `AUTO`（自动建 enabled=1）/ `AUTO_DISABLED`（自动建但需人工开启）。同时检测反向孤儿节点（意图树有、服务端无）。
- **阶段三（多业务域才做）**：抽 `t_mcp_tool_registry` 独立表，意图树回归 KB/SYSTEM 本职。

**升级判断标准**：工具 ≤6 手工可控；7-20 必须开 DISCOVER_ONLY 否则一定漏配；≥20 或多业务域必须重构。

**零改代码的替代方案**：按业务域拆 mcp-server（starline / enterprise），工具集天然隔离，server 内部全量注册——这是 MCP 生态通行做法（Cursor/Claude Desktop/Cline 都这样）。删完 bit/enterprise 后正好只剩一个域，不存在「工具混在一起」问题。

### 【重要澄清】意图树不是向量 RAG

核查 `rag/core/intent/` 目录：**零处 embedding/vector/embed 引用**。`DefaultIntentClassifier.classifyTargets()` 是**纯 LLM 打分**——把所有 KB 叶子节点拼进 prompt 让 LLM 逐个给分，没有向量检索。

项目里实际有三层不同的检索，别混：
1. **意图树分类** = LLM 打分（不是向量），解决「该查哪个 Collection」，KB 节点通常 10-30 个，prompt 能装下
2. **知识库 chunk 检索** = `VectorSearchChannel` + `embedAndNormalize` + 向量库 + RRF + Rerank，这才是真 RAG，解决「库里哪段内容」
3. **Tool RAG（若做）** = 向量检索工具描述，是**第三套**

**可复用的只有底层原子能力** `infra-ai/EmbeddingService.embed()`（已有 `RoutingEmbeddingService` 实现）。索引对象、相关性语义、结果用途三者都不同，不能直接复用索引。

**难度关键洞察**：工具数量少时（4-60 个）**根本不需要向量数据库**——把所有工具描述 embed 后缓存在 JVM 内存 `Map<String, float[]>`，检索时算几十次余弦相似度，微秒级，不需要 Milvus/pgvector。难度从「养一套向量库」降到「10 行余弦计算 + 缓存失效处理」。

**设计要点**：Tool RAG 只应做**召回**（缩减候选到 topK），最终选择仍由 LLM 做。即「向量召回 + LLM 精排」两层结构，与知识库 RAG 的模式一致。不要让向量直接决定调哪个工具——语义相似 ≠ 该用这个工具（如「帮我盯着开票」语义上最像 `search_artist_events` 但该调 `create_reminder`）。

**更实用的中间方案**：工具在这个量级时，先用**LLM 打分**（复用意图树的做法，把全部工具名+描述拼进 prompt 让模型选）即可，不够再上向量。

1. **只有有 `ticket_time` 的记录进日历**。没有开票时间就编「假设 19:30 开场」违反不编造原则；全天事件提前 10 分钟 = 前一天 23:50 更没意义。UI 如实提示「该场次尚未公布开票时间，暂不支持提醒」。
2. **`remind_at` 字段删除**——提前量固定 10 分钟，由 `VALARM:-PT10M` 表达，不需要存绝对时间。这是个大简化。
3. **时区必须写 `DTSTART;TZID=Asia/Shanghai`**，漏了会被当 UTC，提醒错 8 小时。验证必须导进 Google 日历看，本地看不出来。
4. **`UID` 用 `starline-reminder-{id}@starline`**——稳定 UID 让日历里是「更新」而非「新增一条」。
5. **新增 `TOO_CLOSE_TO_NOTIFY` 校验**：开票时间距今不足 10 分钟直接拒绝，否则订阅还没刷新提醒根本不会响，用户以为设成功了。
6. **`/starline/calendar.ics` 必须加鉴权白名单**（日历 App 无 Cookie），但 `/starline/calendar-token` 仍需登录。

**删除清单（精确）**：`StarlineMailProperties`、`StarlineReminderScheduler`、`StarlineBadCaseDetector` 三个类整体删除；`pom.xml` 删 mail starter；DO/VO/Request 删 9 个字段；前端删邮箱输入与展示；compose/.env.example 删 `STARLINE_EMAIL_*`；`application.yaml` 删 `badcase.detectors.starline-delivery`。

**保留**：`STARLINE_RULE_VIOLATION` bad case 上报（Agent 传不合规参数时仍要检测），`sha256` 幂等键逻辑。

**新增**：`StarlineCalendarTokenService`（新建表 `t_starline_calendar_token`，支持重置）、`StarlineIcsBuilder`（ICS 生成 + 转义 + VALARM）、`StarlineCalendarController`。前端加日历订阅卡片（iOS/Android/Outlook 三端引导 + 复制 + 重置）。

**工作量约 1.5 天。实施顺序关键点：阶段 2「删代码」必须验证应用能启动**——最容易漏的是 pom 里的 mail starter 没删但类已删，启动报注入失败。
