# 日志持久化与降噪改造技术方案（交付 Codex 执行）

> 目标：给 `starline-api` 加文件日志 + 轮转，让日志在容器重建后不丢；同时把「路由不存在的 404」从 ERROR 降级，避免淹没真实故障。
>
> 依据：本方案所有文件路径、行号、实测数据均经本地源码与服务器实地核查（2026-10-24）。**未修改任何项目文件。**

---

## 0. 现状实测（为什么必须改）

| 检查项                               | 实测结果                                                 | 后果                                                 |
| --------------------------------- | ---------------------------------------------------- | -------------------------------------------------- |
| 容器日志驱动                            | `json-file`，无 log-opts                               | 只落 `/var/lib/docker/containers/<id>/<id>-json.log` |
| `/etc/docker/daemon.json`         | 只有 `registry-mirrors`，**无日志轮转**                      | json-file 可能无限增长                                   |
| 容器内 `/app`                        | 只有 `application.yaml` + `starline.jar`，**无 logs 目录** | 无文件日志                                              |
| 项目 `logback*.xml` / `log4j2*.xml` | **不存在**                                              | 走 Spring Boot 默认 console-only                      |
| `application.yaml` 的 `logging` 段  | **不存在**                                              | 无级别控制、无文件输出                                        |
| 当前容器日志量                           | **631 行 / 129KB**（容器 18:46 启动）                       | 之前 46 小时的日志已随旧容器消失                                 |

**核心结论**：日志只存在于容器生命周期内，容器一重建就全丢。这是排查 bad case 和 Agent 异常的根本障碍。

## 1. 改造一：文件日志 + 轮转

### 1.1 输出路径选择

**推荐路径：`/app/logs`**（容器内），挂载到宿主机 `./logs`。

理由：`/app` 已经是现有挂载点所在目录（`starline.jar`、`application.yaml` 都在这），保持一致，运维时只需要看一个目录。

### 1.2 配置方式：用 Spring Boot 原生配置（不引入 logback.xml）

**为什么不用 logback.xml**：Spring Boot 的 `logging.*` 属性已经能完整表达「文件 + 轮转 + 级别 + 分文件」，引入 logback.xml 反而会**接管全部日志配置**，导致现有 `application.yaml` 里的级别控制失效，增加维护成本。

**改动文件**：`resources/docker/server/releases/starline-20261022/application.yaml`（部署用）  
以及 `bootstrap/src/main/resources/application.yaml`（本地开发用，可选，见 1.4）

在 `server:` 段之后、`spring:` 段之前（或文件末尾）追加：

```yaml
logging:
  file:
    name: /app/logs/starline.log
  logback:
    rollingpolicy:
      max-file-size: 100MB
      max-history: 7
      total-size-cap: 1GB
      clean-history-on-start: false
  level:
    root: INFO
    com.nageoffer.ai.starlineagent: INFO
    # 降噪：Spring 资源未找到（本质 404）不该占 ERROR
    org.springframework.web.servlet.resource: WARN
  pattern:
    file: '%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level ${PID:- } --- [%15.15thread] %-40.40logger{39} : %msg%n'
    console: '%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level ${PID:- } --- [%15.15thread] %-40.40logger{39} : %msg%n'
```

**关键点说明**：

| 配置                     | 作用                   | 注意                              |
| ---------------------- | -------------------- | ------------------------------- |
| `logging.file.name`    | 同时输出到文件**和** console | 设了这个，console 不会消失               |
| `max-file-size: 100MB` | 单文件上限                | 超出即滚动                           |
| `max-history: 7`       | 保留 7 天               | 按天 + 按大小双重滚动                    |
| `total-size-cap: 1GB`  | 总量硬上限                | **必须有**，防止撑爆磁盘                  |
| `logging.pattern.file` | 文件格式与 console 对齐     | 保证 `docker logs` 和文件内容一致，便于交叉比对 |

### 1.3 compose 挂载

**改动文件**：`resources/docker/server/starline-app.compose.yaml`

`starline-api` 服务的 `volumes` 段（当前 2 项），追加一项：

```yaml
    volumes:
      - ./starline.jar:/app/starline.jar:ro
      - ./application.yaml:/app/application.yaml:ro
      - ./logs:/app/logs          # 新增：日志落宿主机，容器重建不丢
```

> **注意**：不要加 `:ro`（日志要写）。宿主机目录 `~/starline-infra/releases/starline-20261022/logs` 需提前创建，否则 Docker 会用 root 创建，可能导致容器内写入权限问题。更稳妥的做法是显式 `mkdir -p` 并确认属主。

**权限处理**（重要）：容器内进程以 root 运行（`eclipse-temurin:17-jre` 默认 root），挂载目录由 Docker 自动创建时属主是 root，无权限问题。但若宿主机预先用普通用户创建了该目录，需确认：

```bash
mkdir -p ~/starline-infra/releases/starline-20261022/logs
```

### 1.4 本地开发配置（可选）

`bootstrap/src/main/resources/application.yaml` 建议只加：

```yaml
logging:
  level:
    com.nageoffer.ai.starlineagent: INFO
```

**不要**在本地配置里写 `logging.file.name: /app/logs/...`——Windows 上没有 `/app` 路径，会导致启动失败。

## 2. 改造二：探活噪声降级（真正的根因修复）

### 2.1 问题定位

`framework/.../web/GlobalExceptionHandler.java` 第 157-165 行：

```java
@ExceptionHandler(value = Throwable.class)
public ResponseEntity<Result<Void>> defaultErrorHandler(HttpServletRequest request,
                                                       HttpServletResponse response,
                                                       Throwable throwable) {
    log.error("[{}] {} ", request.getMethod(), getUrl(request), throwable);
    return jsonError(response, Results.failure());
}
```

这个兜底 handler 会把**所有**未匹配的异常都打成 ERROR。而 Spring 6.1+ 对「找不到路由」抛出的是 `NoResourceFoundException`（属于 `Throwable`），于是每访问一个不存在的路径，就产生一条带完整堆栈的 ERROR。

**实测证据**：当前 11 条 ERROR **全部**是这类：

```
org.springframework.web.servlet.resource.NoResourceFoundException:
No static resource rag/v3/chat for request '/api/starlineagent/rag/v3/chat'.
```

来源是 workflow 接口（`/rag/v3/chat`、`/conversations`、`/rag/traces/runs`），在 agent 引擎下已下线，**404 是预期行为**。

### 2.2 修复方案：单独加一个 handler 降级

在 `GlobalExceptionHandler` 中，`defaultErrorHandler` **之前**插入：

```java
/**
 * 路由不存在的 404 属预期行为（前端旧链接、探活脚本、已下线路由），
 * 用 ERROR 打完整堆栈会淹没真实故障，这里降为 WARN 且不打印堆栈。
 */
@ExceptionHandler(value = NoResourceFoundException.class)
public ResponseEntity<Result<Void>> noResourceFoundHandler(HttpServletRequest request,
                                                           HttpServletResponse response,
                                                           NoResourceFoundException ex) {
    log.warn("[{}] {} 路由不存在: {}", request.getMethod(), getUrl(request), ex.getResourcePath());
    return jsonError(response, Results.failure(BaseErrorCode.CLIENT_ERROR.code(), "请求的资源不存在"));
}
```

**需要新增 import**：

```java
import org.springframework.web.servlet.resource.NoResourceFoundException;
```

**关键点**：

- **不打印堆栈**（`log.warn` 只带 `ex.getResourcePath()`）—— 这是降噪的核心
- 返回 `CLIENT_ERROR`（4xx 语义）而非默认的 `Results.failure()`，更准确
- **必须放在 `defaultErrorHandler` 之前**（Spring 会选最具体的 handler，位置不影响，但按可读性放前面）
- 保持 `jsonError` 的既有约定（HTTP 200 + 业务错误码），不破坏前端

### 2.3 为什么不只在日志配置里过滤

也可以用 `logging.level.org.springframework.web.servlet.resource: WARN`（方案 1.2 已含）在**框架层**抑制。

但两者作用不同：

| 手段                               | 效果                                                        |
| -------------------------------- | --------------------------------------------------------- |
| `logging.level...resource: WARN` | 抑制 Spring 内部日志，**但你的 `defaultErrorHandler` 仍会用 ERROR 打印** |
| 新增 `@ExceptionHandler`           | **从根上**把它从 ERROR 降为 WARN                                  |

**两个都要做**：`@ExceptionHandler` 是根因修复，`logging.level` 是额外保险。

## 3. 改造三：探活脚本噪声隔离（可选但推荐）

### 3.1 现状

服务器上存在 workflow 退役验证脚本：

```
/home/ubuntu/starline-infra/releases/starline-20261022/verify-workflow-retirement.py
/home/ubuntu/starline-infra/releases/starline-20261022/.workflow-upload-20261024/verify-workflow-retirement.py
```

它会主动请求已下线的 workflow 路由（如 `/rag/v3/chat?question=retirement-probe`），**产生大量预期内 404**。

### 3.2 处理建议

**这是运维动作，不是代码改动**，二选一：

- **方案 A（推荐）**：验证完成后**删除/移走**该脚本，避免持续产生噪声
- **方案 B**：验证保留脚本，但改为**非工作时间手动执行**，不要留在定时任务里

⚠️ 按只读原则，**本方案不建议 Codex 自动删除服务器文件**，请用户确认后自行处理。

## 4. 可选改造：Docker 层兜底轮转

如果不想改应用配置，也可以在 `/etc/docker/daemon.json` 加全局轮转：

```json
{
  "registry-mirrors": ["https://mirror.ccs.tencentyun.com"],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  }
}
```

**注意**：

- 修改后需 `sudo systemctl restart docker`（**会重启所有容器**，需停机窗口）
- 只对**新建**容器生效，现有容器需重建
- **这是兜底，不能替代应用层文件日志**（json-file 内容难读、不便 grep）

**建议**：应用层文件日志（第 1 节）是主线，daemon.json 可作为补充，但不是必须。

## 8. 风险与注意

1. **版本已核实**：`pom.xml` 第 17 行 `spring-boot.version = 4.1.0`，运行时日志显示 `spring-webmvc-7.0.8.jar`（Spring Framework 7.0.8）。`NoResourceFoundException` 自 Spring 6.1 引入，**当前版本可用**。`logging.file.name` 也是 Spring Boot 2.4+ 的正确写法（旧版 `logging.file` 已废弃）。
2. **不要引入 `logback-spring.xml`**：会接管全部日志配置，与现有 `logging.*` 冲突，且增加维护成本。
3. **`max-history` 按天滚动 vs 按大小滚动**：Spring Boot 的 `rollingpolicy` 同时支持两者，但 `max-history` 只在**按天滚动**时精确生效；按大小滚动用 `total-size-cap` 兜底。两者都配是正确做法。
4. **磁盘监控**：`total-size-cap: 1GB` 是硬上限，但滚动文件数 × 单文件大小仍可能略超。当前服务器磁盘 30%（41G 可用），1GB 上限安全。
5. **`NoResourceFoundException` 的可用性**：已核实 `spring-boot.version = 4.1.0`（`pom.xml` 第 17 行），Spring Framework 7.0.8，该类自 6.1 引入，**可用**。
6. **不要给 `defaultErrorHandler` 降级**：只降 `NoResourceFoundException`，**其他所有异常必须保持 ERROR**。这是红线。
7. **日志中的敏感信息**：`application.yaml` 里有数据库密码、API Key。当前 `log.error` 打印的是 URL 和异常，不含配置值，风险可控。但如果后续加了请求体日志，需做脱敏（参考 `AgentAuditSerializer` 的 `SECRET_KEY` 正则）。
