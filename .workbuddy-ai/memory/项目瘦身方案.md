# starlineAgent 项目瘦身方案

> 基于 2026-10-25 实测扫描。所有数字来自 `Get-ChildItem` 递归统计 + jar 内 `BOOT-INF/lib` 逐项解析。
> 本文只给建议，不直接改项目文件（按项目只读约定，落地交给 Codex）。

---

## 一、账本：1.07 GB 是怎么来的

| 目录 | 体积 | 性质 | 判断 |
|---|---|---|---|
| `.local-backups/` | **434 MB** | 内含 2 个 214MB fat jar | ❌ 纯浪费 |
| `frontend/node_modules/` | 371 MB | 前端依赖（含 40MB 残留缓存） | ⚠️ 基本合理 |
| `bootstrap/target/` | **213.5 MB** | 单个 fat jar | ⚠️ 可重建 |
| `mcp-server/target/` | 29.1 MB | 构建产物 | ⚠️ 可重建 |
| `assets/` | 21.5 MB | 架构图 PNG（十几张 1~2MB） | ✅ 合理 |
| 其余 target（7 个模块） | 10.3 MB | 构建产物 | ⚠️ 可重建 |
| `frontend/dist/` | 7.1 MB | 前端产物 | ⚠️ 可重建 |
| 源码 + 资源 + 文档 | 约 4 MB | — | ✅ 合理 |

**结论：真正属于「不该存在」的只有 434MB 的备份目录。** 其余是开发必然产物，只是缺一次清理。

## 二、P0：立刻可回收 469 MB（零风险）

### 2.1 备份目录里的 fat jar（428 MB）

`.local-backups/` 下两个目录各存了一份 214MB 的 jar：

```
badcase-pool-upload-20261025/starline.jar       214 MB   12:55
feedback-withdrawal-20261025T0521Z/starline.jar 214 MB   13:17
```

**相隔 22 分钟，SHA256 不同（内嵌时间戳变了），但功能完全等价。**

这两份 jar 的本质问题是：**备份的应该是「可重建的源码快照」，不是「214MB 的构建产物」**。

`docs/design/workflow-retirement.md` 里写得很清楚，`.local-backups` 的用途是：

> 本地按将修改的文件保存**源码快照和清单**……避免把用户此前所有未提交内容混入自动基线提交

**但 starline.jar 不是源码，是构建物。** 它占了这个目录 99% 的体积，却提供不了任何「源码快照」的价值 —— 因为只要有源码，`mvn package` 随时能重新生成。

**执行：**

```bash
cd C:/Users/cjx/Desktop/starlineAgent
find .local-backups -name "starline.jar" -delete
find .local-backups -name "frontend.tar.gz" -delete
du -sh .local-backups
```

**保留**：`.sql` / `.yaml` / `.sh` / `.py` / `SHA256SUMS` / `.zip` 源码快照 —— 这些加起来不到 1MB，是备份目录真正的价值所在。

### 2.2 vite 残留临时缓存（约 40 MB）

```
frontend/node_modules/.vite/deps_temp_14965ef2   43 MB
```

`deps_temp_*` 是 vite 预构建失败或中断后留下的临时目录，正常情况下会在下次构建时自动清理。你这份是从 10-24 那次构建残留的。

```bash
rm -rf frontend/node_modules/.vite/deps_temp_*
```

**注意别删整个 `.vite`**，里面的 `deps` 是有效的预构建缓存，删了下次启动会重新构建（多等 10~30 秒）。只删 `deps_temp_*`。

## 三、P1：随时可清的构建产物（260 MB）

这些不是浪费，是「用完该扫」的东西：

```bash
mvn clean                      # 各模块 target 约 253 MB
rm -rf frontend/dist           # 7 MB
```

**建议加进日常习惯**：投简历/传项目/备份到网盘之前先 `mvn clean`，否则你传的是 250MB 的编译中间物。

**清理后预计**：1.07 GB → **约 340 MB**。

## 四、P2：jar 本身能瘦 20 MB（214 → 194）

fat jar 共 **416 个依赖，213.8 MB**。解压后 = 压缩后（因为内嵌 jar 已 deflate，`spring-boot-maven-plugin` 压不动）。

两处可以直接拿掉，都在依赖树末端，改动小、风险低：

### 4.1 排除 `sqlite-jdbc`：省 11.4 MB

**你整个源码零处引用 sqlite**（我 grep 过 `*.java`、`*.yaml`、`pom.xml`，全空）。

但它被打了进去：

```
io.agentscope:agentscope-core:2.0.2 → sqlite-jdbc:3.53.2.0 (11.4 MB)
```

AgentScope 用它做本地会话存储，你用的是 PostgreSQL，完全用不到。

**改法**（根 `pom.xml`，`agentscope-core` 的声明处，约 183 行）：

```xml
<dependency>
    <groupId>io.agentscope</groupId>
    <artifactId>agentscope-core</artifactId>
    <version>${agentscope.version}</version>
    <exclusions>
        <exclusion>
            <groupId>org.xerial</groupId>
            <artifactId>sqlite-jdbc</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

**验证**：改完 `mvn -pl bootstrap -am package`，然后

```bash
unzip -l bootstrap/target/bootstrap-0.0.1-SNAPSHOT.jar | grep sqlite
```

应该无输出。再启动一次应用，确认没有 `ClassNotFoundException: org.sqlite.JDBC`。

### 4.2 排除 `netty-codec-native-quic`：省 11.2 MB

它带进来 **5 个平台的 native 包**：

```
netty-codec-native-quic-4.2.15.Final-linux-x86_64.jar    2.6 MB
netty-codec-native-quic-4.2.15.Final-linux-aarch_64.jar  2.5 MB
netty-codec-native-quic-4.2.15.Final-osx-x86_64.jar      2.4 MB
netty-codec-native-quic-4.2.15.Final-osx-aarch_64.jar    2.2 MB
netty-codec-native-quic-4.2.15.Final-windows-x86_64.jar  1.5 MB
```

**HTTP/3 / QUIC 整个项目零使用**（我 grep 过 `http3`、`quic`，命中的都是 okhttp 包名，不是 QUIC）。你跑的是 HTTP/1.1 + WebSocket/SSE，用不上 QUIC。

```xml
<exclusion>
    <groupId>io.netty</groupId>
    <artifactId>netty-codec-native-quic</artifactId>
</exclusion>
```

**放在哪**：如果 quic 是通过 `netty-codec-http3` 或 `agentscope` 传进来的，在对应声明处排除。先用这条命令确认来源：

```bash
mvn dependency:tree -Dincludes=io.netty:netty-codec-native-quic -pl bootstrap -am
```

### 4.3 不建议动的部分

| 依赖 | 体积 | 为什么不动 |
|---|---|---|
| POI 全家桶（34 个文件） | 19.1 MB | `xmlbeans` + `poi-ooxml` 是解析 docx/xlsx 的必需，知识库上传要用 |
| Milvus SDK + gRPC | 20.9 MB | `MilvusVectorStoreService` 在用 |
| elasticsearch-java | 13.2 MB | `EsKeywordIndexService` / `EsKeywordRetrieverService` 在用 |
| **Jackson 2.21.4 + 3.1.4 并存** | 约 5 MB | 根 pom 显式引 `spring-boot-jackson2` 做 Boot 4 迁移兼容，**有意为之**。面试可以主动说，别当 bug |
| bcprov-jdk18on | 8.5 MB | S3/OSS 签名必需 |

**唯一可能再砍的是 POI**：如果知识库不支持 doc/xls 上传，`poi` + `xmlbeans` 能省掉一部分。但这要看产品需求，不建议为了 19MB 动。

## 五、P3：防复发 —— 三件流程改造（真正值钱的部分）

前面几步只是「把已经发生的问题清掉」，**不改造流程，一个月后又会涨回来**。

### 5.1 备份目录只存源码，不存构建物（关键）

**问题**：现在 `deploy-*.sh` 里有这样的行：

```bash
cp -p "$release/starline.jar" "$backup/starline.jar"
```

这是**服务器上**的回滚备份（`$release_dir/backups/mcp-deploy-<ts>/`），每部署一次就在服务器留一份 214MB —— 那是服务器的磁盘问题，本地不受影响。

**本地 `.local-backups` 的 214MB 是另一回事**：它是修改前把 `bootstrap/target/*.jar` 拷进来当快照。**这个动作本身没有价值**，因为 jar 能重造。

**建议在项目文档里写死一条规则**：

```
.local-backups/<task>/ 只允许存放：
  - 源码文件（.java / .ts / .tsx）
  - 配置与脚本（.yaml / .sql / .sh / .ps1 / .py / .nginx.conf）
  - 文件清单与哈希（MANIFEST.md / SHA256SUMS）
禁止存放：
  - 构建产物（*.jar / *.tar.gz / dist/ / target/）
  - 依赖目录（node_modules/）
  - 凭据（.env）
```

**理由一句话**：jar 是 `mvn package` 的输出，源码才是不可再生的。存 jar 等于用 214MB 换 0 信息量。

### 5.2 部署从 `scp` 换成 `rsync`（收益最大的一条）

**现状**：`scripts/deploy-badcase-candidate-pool.ps1` 用的是

```powershell
& scp @taskSsh @taskUpload "ubuntu@139.199.191.109:$taskRemoteStage/"
```

`scp` **每次都完整传 214MB**。你的 compose 是 bind mount：

```yaml
volumes:
  - ./starline.jar:/app/starline.jar:ro
command: ['java', '-jar', '/app/starline.jar']
```

所以每次部署都是「本地打 214MB → 传 214MB → 挂载」。**在 4G/家宽上行下，这一步要几分钟，而且 99% 的字节没变化**（依赖层完全一样，只有 `BOOT-INF/classes` 里几 MB 变了）。

**改成 rsync**：

```bash
rsync -avz --partial --inplace \
  -e "ssh -i ~/.ssh/id_ed25519 -o BatchMode=yes" \
  bootstrap/target/bootstrap-0.0.1-SNAPSHOT.jar \
  ubuntu@139.199.191.109:/path/to/.stage/starline.jar
```

**rsync 的滚动校验只传差异块**，214MB 的 jar 里如果只有 3MB 变了，实际传输量约 3~5MB。**部署时间从几分钟降到十几秒。**

**前置确认**（服务器是 Ubuntu，通常自带 rsync）：

```bash
ssh -i ~/.ssh/id_ed25519 ubuntu@139.199.191.109 'rsync --version | head -1'
```

如果没装：`sudo apt install rsync`（这属于服务器写操作，按约定要你或 Codex 执行）。

**注意**：`--inplace` 必须加。默认 rsync 会在目标端建临时文件再 rename，而你的 jar 是 bind mount 进容器的，rename 会导致容器看到旧 inode。用 `--inplace` 原地写才安全。**另外必须串行执行**：传完再 `docker compose up -d --force-recreate`，不能一边传一边重启。

### 5.3 可选：分层 jar（要改启动方式，收益递减）

Spring Boot 支持把 jar 拆成层：

```bash
java -Djarmode=tools -jar bootstrap/target/bootstrap-0.0.1-SNAPSHOT.jar \
  extract --layers --launcher --destination out/
# 产出：
#   out/dependencies/        ← 200MB，代码不改就永远不变
#   out/spring-boot-loader/
#   out/snapshot-dependencies/
#   out/application/         ← 你的 classes，几 MB
```

配合 rsync，日常部署只传 `application/` 那几 MB。

**代价**：compose 的启动命令要从

```yaml
command: ['java', '-jar', '/app/starline.jar']
```

改成

```yaml
command: ['java', '-cp', '/app/classes:/app/libs/*', 'com.nageforge...BootstrapApplication']
```

或者挂整个 `out/` 目录进去跑 `JarLauncher`。

**我的判断：先做 5.2（rsync），别做 5.3。** 理由：

- rsync 已经能把传输量压到「只传变化的块」，效果和分层几乎一样
- 5.3 要改启动命令、改 compose、改回滚脚本，**一旦改错，容器起不来**
- 而且分层后 `java -jar` 这个最简单的启动方式就没了，排查问题多一层

**除非**你以后要上 K8s / 多副本滚动更新，那时分层的价值才真正体现（镜像层复用）。现在单机 compose，不值。

## 六、执行清单（按顺序，含验收）

### 阶段 1：立即可做（728 MB → 剩约 340 MB）

```bash
cd C:/Users/cjx/Desktop/starlineAgent

# ① 删备份里的构建物
find .local-backups -name "starline.jar" -delete
find .local-backups -name "frontend.tar.gz" -delete

# ② 清构建产物
mvn clean
rm -rf frontend/dist

# ③ 清 vite 残留缓存
rm -rf frontend/node_modules/.vite/deps_temp_*

# 验收
du -sh .
du -sh .local-backups frontend
```

**预期**：`.local-backups` < 2 MB，总计约 340 MB。

### 阶段 2：jar 瘦身（-20 MB，需改 pom，交 Codex）

1. 根 `pom.xml` 给 `agentscope-core` 加 `sqlite-jdbc` 排除
2. `mvn dependency:tree -Dincludes=io.netty:netty-codec-native-quic` 确认来源后排除
3. `mvn -pl bootstrap -am package -DskipTests`
4. 验收：
   ```bash
   ls -lh bootstrap/target/*.jar          # 期望 ≈ 194 MB，原 213.5 MB
   unzip -l bootstrap/target/*.jar | grep -cE "sqlite|native-quic"   # 期望 0
   ```
5. **启动应用验证**（最关键的验收）：能正常启动、能调 MCP 工具、能查知识库

### 阶段 3：流程改造（交 Codex，防复发）

1. `scripts/deploy-*.ps1` / `*.sh` 里 `scp` 改 `rsync --inplace --partial`
2. 项目文档加一条 `.local-backups` 内容规范（只存源码，不存构建物）
3. 服务器备份目录加保留策略（例如只留最近 3 份）—— 这属于服务器改动，需你或 Codex 执行

## 七、一句话总结

> **434 MB 是备份目录里不该存在的 jar，250 MB 是随时可重建的编译产物，40 MB 是缓存残留。**
>
> **真正该改的不是「删文件」，是两条习惯**：备份只存源码不存构建物；部署用 rsync 不用 scp。
>
> **jar 本身从 214 降到 194 是锦上添花**，值 20 MB，但要动 pom、要回归验证，优先级低于前两条。
