## 项目经验

### 一、starlineAgent — AI Agent 平台（个人深度实践项目）

**技术栈**：Java 17 / Spring Boot / Spring Cloud / MyBatis-Plus / PostgreSQL / Redis / React / MCP / DeepSeek
**架构**：bootstrap（启动）、agent（Agent 运行时）、rag（检索）、mcp-server（工具服务端）、starline（业务域）多模块

**项目简介**：面向"演出信息查询 + 开票提醒"场景的 AI Agent 平台，目标是把 Agent 从"能跑的 demo"做成"可审计、可回归、可上线的系统"，完整验证了从工具定义、检索链路、上下文治理到评测闭环的工程化路径。

**① 自研 MCP 工具服务端，把工具调用做成可审计的生产接口**

- 基于 MCP Streamable HTTP 协议实现工具服务端，累计实现 **24 个工具**（覆盖电商交易、企业 OA、通用检索三类场景），端点单口暴露，客户端零适配
- **启动期强制校验**：每个工具必须声明 `readOnlyHint`（只读 / 写入）与完整参数描述，任一项缺失服务直接启动失败 —— 把"写操作漏标成只读、模型静默执行扣款"这类事故挡在部署之前
- **工具装配四层过滤**：服务端发现 → 授权白名单 → 内置工具名碰撞保护 → 指纹缓存重建。工具下线或改名时自动降级为告警而不阻塞启动，避免单个工具故障导致整个 Agent 起不来
- **身份与错误隔离**：用户身份经协议扩展字段 `_meta` 透传，明确不进入模型可控的工具参数，防止模型被诱导越权查询他人数据；工具异常时只向模型返回"调用失败，请稍后重试"，底层异常仅落日志 —— 避免 SQL 片段、连接串被模型当作业务结论转述给用户

**② RAG 多通道检索与意图路由**

- 向量 + 关键词 + 图三通道并行召回，**RRF 融合**后统一 Rerank 截断注入上下文；Query 改写含子问题拆分，应对多意图复合问句
- 意图树路由到知识库 Collection，采用 **LLM 打分而非向量检索**，与向量通道解耦 —— 避免"语义相近但领域不同"的误路由
- 外部联网通道设计为**静默降级**：任何超时或解析异常均不向上抛出，返回空结果并记录耗时，保证第三方服务故障不影响本地知识库检索链路

**③ 上下文工程与长期记忆**

- **双策略上下文治理**：先按工具结果裁剪（Trimmer），超预算（默认 120 万字符）触发摘要压缩（Compactor），压缩结果落表留痕，支持事后复盘"模型当时看到了什么"
- **长期记忆流水线**：抽取 → 判定 → 合并三段式，对新记忆做 CREATE / MERGE / SKIP / DELETE 决策，抑制重复记忆无限累积

**④ Agent 评测与 bad case 体系**

- 自建断言式评测框架，覆盖**记忆、上下文压缩、并发、运行闸门审计等 6 套回归集**，支持 `expectTools` / `expectAll` 类断言
- 报告生成器**强制校验数据集指纹、轮次计划、计量条件**，三者任一项不一致直接拒绝给出对比结论 —— 防止"两组条件不同却算出提升"的伪结论
- **全链路审计**：每次运行落 run / run_node 两级表，含完整入参出参、耗时、状态，支撑"工具失败 / 耗时异常 / 空结果"三类 bad case 自动识别

**⑤ 业务闭环设计**

- 按"意图组织"而非"API 翻译"设计工具：`search_artist_events` 单工具内部完成实体过滤 → 来源可信度打标 → 时效判定 → 售票状态抽取 → 排序 → 提示组装 **6 步判定**，对外只暴露 1 个工具而不是 6 个，把编排责任收进服务端
- 判定结果**下沉为字段**（来源层级 / 是否过期 / 阶段 / 能否购票），模型的职责从"推理判断"降级为"读字段组织语言"，从源头压制幻觉

## 五、面试必须提前准备好的四个回答

### Q2「这项目有真实用户吗？」

答：没有，本地与测试环境验证，未上生产。

**但补一句**——这恰恰说明你知道生产能力缺口在哪：

> 没上生产。我在设计时明确标了几条上线阻塞项：MCP 服务端只绑本机、身份靠协议扩展字段透传，这套只在"同机单应用"前提下成立；一旦要对外暴露，身份链路必须换成 OAuth。这个判断我写在代码注释里了。

**这个回答比"有几百用户"更让面试官信任你。**

### Q3「24 个工具，模型怎么选得对？」

答：讲三层。

1. **权限层**：不是全部注册给模型，服务端发现后还要过授权白名单，业务域外的工具模型根本看不见
2. **描述层**：description 是模型唯一的判断依据，所以写"什么时候不该调"比写"能做什么"更重要
3. **规模层**：工具数超过 10-30 个后选择准确率会下降，我评估过 Tool RAG 和延迟加载两条路，但按官方门槛算下来当前规模全量注入更优，所以没上

**第 3 点最关键**——它证明你做过技术选型判断，而不是"什么火就上什么"。

### Q4「你怎么知道 Agent 变好了还是变坏了？」

答：讲评测框架 + 一个具体约束。

> 我自建了断言式回归集，跑对比时必须过三道校验：数据集指纹、轮次计划、计量条件。三者不一致，报告生成器直接拒绝出结论。因为"通过率 82% → 85%"这种数字，如果不是同一套条件跑出来的，就是假的。

**这个回答会让人记住你。**

# 附录：原简历六项工作的技术含量评估

## A. 判断标准（四条）

「技术含量高」不是「听起来复杂」。用这四条判断：

| 标准 | 含义 |
|---|---|
| 问题是否真实 | 不是为汇报而硬造的痛点 |
| 是否有取舍 | 只有一个方案说明没比较过；有备选、有放弃才是真做过选择 |
| 是否有非显然细节 | 别人想不到的坑，你踩过并解决了 |
| 指标是否有意义 | 数字本身能不能说明问题（「100% 准确率」就很难说明） |

## B. 逐条评估

### 第一档：真难点，必须完整保留

**② 预算表单并发互斥（Redis 可续期锁 + WebSocket 心跳 + 三重兜底）**

技术含量第一。难点不在「加锁」，在于**解锁**——用户关网页 / 断网 / 手机关机，服务器收不到任何通知。这是分布式系统的崩溃检测问题（CAP 里最脏的部分）。「三重兜底」说明考虑过多个失败模式，「可续期」说明理解 TTL 与业务耗时的关系，不只是会在 `SETNX` 打转。**能讲 20 分钟不重复的深水区。**

**① 日志全链路零丢失（Log4j2+Disruptor / Logstash 死信 / ES 写入调优）**

技术深度第二，也是唯一一条三层都有非显然细节的。最有价值的是采集层——选了 Disruptor 的代价是内存丢数据，必须在采集层用死信补回来，**说明取舍是想过的，而且知道代价在哪**。

⚠️ 必答追问：「吞吐 +80% 而接口耗时 −90%，同时改善可能吗？」
正确解释：原先同步写 ES 阻塞业务线程，解耦后业务线程不等 IO，所以吞吐和延迟同时改善。**不准备这一点会被当成编数据。**

### 第二档：技术不最深，但对 Agent 岗说服力最强

**⑤ 支付状态机 + 幂等**

技术难度中等（状态机模式不难），但和 Agent 项目的确认卡机制是同一个问题：严格定义合法状态流转 ↔ 确认卡生命周期；统一变更入口 ↔ 所有写工具经 `McpToolProxy`；事务原子 ↔ 工具失败回滚；幂等拦截 ↔ 模型重复调用不能重复扣款。

⚠️ 「100% 准确率」是风险数字。面试官会问「怎么保证 100%、怎么测的」。改法见 D 节。

**④ 多入口统一治理（门面 + 责任链 100+ 规则）**

技术难度中等偏下，但**架构判断力最强**——识别出「四个入口各自校验导致规则漂移」这个组织层面问题。与 MCP 工具治理同源：所有创建请求从统一入口进 ↔ 所有工具调用经 `McpToolProxy` 走权限闸门。

⚠️ 唯一缺陷：没有数字。可深挖点是责任链的性能与短路设计。

### 第三档：可压缩，但面试要准备

**⑥ 供应商日终筛查（20 分钟 → 2 分钟）** — 技术中等偏高，但是叠加型优化（布隆过滤器 + 分片并行 + 索引 + 分布式锁），没有单一巧点。真正能深挖的是**布隆过滤器的假阳性取舍**（需二次确认），原文没写，写出来会显得更懂。

**③ 提交流程异步重构（45 秒 → 5 秒）** — **六条里技术含量最低**。CompletableFuture 依赖编排 + 分片并行 + 线程池隔离是标准异步化，很多 3 年的人都会。若必须删一条腾版面，删这条。

## C. 隐藏问题：六条里四条都是「性能优化」

```
⑥ 20 分钟 → 2 分钟    性能
③ 45 秒 → 5 秒        性能
① +80% / −90%        性能
④ 无数字              架构
② 秒级释放            可靠性
⑤ 100%               正确性
```

面试官扫完的印象会是「这人只会调性能，没做过复杂业务建模」。**改写时必须刻意打散类型**，让「可靠性」「正确性」「架构治理」各占一条。

| 保留 | 方式 | 理由 |

| ② 表单并发互斥 | **完整，放第一条** | 技术最深 + 可靠性设计，能讲透 |
| ⑤ 支付状态机幂等 | **完整，放第二条** | 对 Agent 岗迁移价值最高 |
| ① 日志链路零丢失 | 保留但**压到 3 行** | 技术深但不对口，面试再展开 |
| ④ 多入口统一治理 | 保留，**与 ② 合并成一组** | 架构治理能力证明 |
| ⑥ 日终筛查 | 保留，**补一句布隆过滤器取舍** | 成本低、有帮助 |
| ③ 异步重构 | **压到 1 行**或删 | 技术最浅，且与 ②⑥ 同质（都是提速） |
| 编码大赛一等奖 | **单独一行前置** | 稀缺信号，原被埋没 |

**三处措辞必修**

```
① 删掉「（性能提升 90%）」
   ❌ 20 分钟压缩至 2 分钟，性能提升 90%
   ✅ 筛查耗时从 20 分钟压缩至 2 分钟
   理由：「20 分钟变 2 分钟」的直观冲击强于「90%」，且 18/20 的算法在小基数下显得虚

② 「100%」换成可验证表述
   ❌ 实现支付状态回写准确率 100%
   ✅ 从规则层与代码层双层拦截非法状态跳转，上线至今零状态回写错误
   理由：100% 无法自证，零事故可查

③ 修病句
   ❌ 期间曾在获得建行编码大赛一等奖
   ✅ 【单独一行】建行编码大赛一等奖
   理由：「曾在获得」是明显笔误；全行级奖项不该埋在 90 字长句里
```

**面试前必答清单**

| 追问 | 应答要点 |
|---|---|
| 吞吐和延迟怎么同时改善的？ | 同步写 ES 阻塞业务线程 → 异步解耦后业务线程不等 IO |
| 100% 准确率怎么测的？ | 改成「零事故」，讲双层拦截（规则层 + 代码层） |
| 为什么选 Disruptor 不选 MQ？ | 内存队列换吞吐，代价是丢数据风险，所以采集层用死信兜底 |
| 布隆过滤器假阳性怎么处理？ | 预筛后必须回源二次确认，否则会漏掉唯一性冲突 |
| 三重兜底具体是哪三重？ | TTL 到期 / 心跳超时 / 主动清理，三者任一触发即释放 |
