## Langfuse 的能力边界（依据 trace/README.md 实测记录）

**定位**：Langfuse 零采集能力，只是 OTLP 接收端 + LLM 语义渲染层。数据全部由项目自己的中间件产生（`AgentRunTracer`/`StarlineOtelTracingMiddleware`/`AgentTraceEnrichmentMiddleware`/`AgentToolBodyTracer`）。

**摄取分拣三分支**（README 用 ClickHouse `events_full` 表实测）：
1. 认得的键 → 进强类型列 `input`/`output`/`provided_model_name`/`usage_details`/`session_id`（可索引可聚合）
2. 不认得的键 → 落 `metadata_names`/`metadata_values` 数组（存下来了但查不了过滤不了）
3. **span event → 整个丢弃**（项目据此删掉 3 个 event：`starlineagent.tool.awaiting_confirmation`/`.denied`/`.short_circuited`，改写进批 span 的 `observation.output`）

**Langfuse 独有能力**（对应 `AgentTraceAttributes` 的 `langfuse.*` 属性）：
- `observation.type=generation` → 识别为 LLM 调用，才有成本/模型视图
- `usage_details` → token 归一化（input 已减 cached）+ 按模型单价算钱
- `completion_start_time` → **首字延迟 TTFT**
- `session.id`(=conversationId) / `user.id` → Threads 会话视图与成本归因

## RAG workflow 链路适用场景分析（代码实测）

**RAG 是固定七阶段流水线**（`rag/service/pipeline/StreamChatPipeline.execute`）：
1 `loadMemory` → 2 `rewriteQuery`（`rewriteWithSplit`：改写+拆子问题，`RewriteResult(rewrittenQuestion, subQuestions)`）→ 3 `resolveIntents`（意图树：KB/SYSTEM/MCP 三类）→ 4 `handleGuidance`（歧义则直接反问，不硬答）→ 5 `handleSystemOnly`（系统类跳过检索，用节点 promptTemplate 直答）→ 6 `retrieve`（多通道）→ 7 `streamRagResponse`（`sourcesAssembler.assemble` + `citationContextEnricher.enrich` 注入角标 + groundingChunks 落库）

**检索内核**：四通道 `VECTOR`(pgvector，按意图置信度收窄库) / `KEYWORD`(ES) / `GRAPH`(预留未实现) / `WEB`(可配置开启)；后处理链 `Dedup → Fusion → Rerank → EvidenceGate → MetadataEnrichment → ChannelAttribution`。
**EvidenceGate**（证据闸门）是防幻觉硬机制：按整批最高精排分判定，不合格整批丢弃，注释「检索只保证返回最像的 N 条，库里没答案时照样满额返回，下游又只看证据文本非空，噪声必然进提示词」。

**⭐ 重大发现：切 Agent 后 RAG 内核没浪费**。`KnowledgeSearchFacade.search()`（rag/service/）被 `search_knowledge` 工具调用，内部复用：`rewriteWithSplit` → `intentResolver.resolve` → `guidanceService.detectAmbiguity`（歧义反问）→ `retrievalEngine.retrieve`（含证据闸门）→ `citationContextEnricher.stripDocIdAnchors`（主动抹掉 docId）→ `promptService.buildStructuredMessages` → `llmService.chat`（temperature=0）。
注意：这是**二次 LLM 调用**（RAG 当子代理），且 `rewriteWithSplit(query, List.of())` **不喂历史**（注释：主 Agent 手握完整对话，传进来的已是消解过的查询）。

**Agent 模式下真正丢失的四项**：
1. 行内引用角标 + sources 面板（工具内 stripDocIdAnchors 主动抹掉，因「工具不渲染角标」）
2. 流式输出（工具内是阻塞 `llmService.chat`，非 SSE 流）
3. 歧义反问直达用户（变成工具返回值，主 Agent 可能改写或忽略）
4. 路径确定性（RAG 固定 7 步 P95 可预测 vs ReAct 轮数不定）

**RAG 适用场景**：纯知识问答（客服FAQ/产品文档/规章制度）、必须给来源的场景（法务/医疗/合规，引用角标是硬需求）、延迟成本敏感、高并发简单问答、长回答需流式体验。
**Agent 适用场景**：多步操作、写操作(HITL)、问题模糊需探索、需长期记忆与技能、需实时 MCP 工具。
**架构限制**：`EngineGate.tsx:24` 全局二选一，无法按会话/场景分流——这是当前架构的约束。

### options{} 溯源（代码核实）

- `options{}` 不是发给模型的请求字段，而是 **审计/追踪序列化快照**：来源 `io.agentscope.core.model.GenerateOptions`，由 `AgentAuditSerializer.modelInput()`（46-52 行）与 `AgentTraceSerializer.modelParameters()`（167 行起）序列化。

## 豆包/火山方舟 实时信息查询方案（官方文档查证，修正前面判断）

**重要修正：字节不建业务表，靠「强搜索 + 结构化引用 + 域名白名单」。**

### 火山方舟 Responses API 的 web_search 工具（官方文档可查）
```json
{ "type": "web_search", "sources": ["doubao"], "user_location": {...}, "max_keyword": 2, "limit": 10 }
```

**核心能力（对用户项目有直接借鉴价值）：**
1. **结构化引用返回** —— 这是关键：
```json
"content": [{ "type": "output_text", "text": "...",
  "annotations": [{ "type": "url_citation", "title": "...", "url": "...",
                    "site_name": "新浪新闻", "publish_time": "2026-09-04T10:24:00+08:00",
                    "summary": "..." }] }]
```
→ **`site_name` + `publish_time` 直接解决了「来源类型判断」和「时效性判断」两个问题**，不用自己建表存 verified_at

2. **`allowed_domains` / `blocked_domains`**（Messages API）—— 这正是用户 system prompt 里「平台级官方域名清单」的技术落地方式
3. **`user_location`**（country/region/city）—— 优化地域相关搜索，对应「城市筛选」
4. **`sources`** 可配垂直信源：doubao / douyin(抖音百科) / moji(墨迹天气) / toutiao(头条图文)
5. **`max_tool_calls`** 默认 3，限制一轮内工具调用轮次（防失控）
6. `usage.tool_usage_details` 可查到每个搜索源的调用次数（成本可归因）
7. 不支持 caching 与 tools 同用（400 错误）

**官方系统提示词模板的「联网意图判断」三条标准：**
- 时效性：需要最新/实时信息
- 知识盲区：超出知识范围
- 信息不足：知识库无法完整解答

**⚠️ 用户项目与豆包的差距（实测对比）：**
| 能力 | 豆包/方舟 | 用户项目 |
|---|---|---|
| 结构化引用（site_name/publish_time） | ✅ annotations | ❌ youcom_search 只返网页片段 |
| 域名白名单 | ✅ allowed_domains | ❌ 无 |
| 位置感知 | ✅ user_location | ❌ 无 |
| 多垂直信源 | ✅ doubao/douyin/moji/toutiao | ❌ 仅 You.com |

**结论：之前建议「建 t_artist_event 表」属于过度设计。** 更贴近大厂实践的路径是：
1. 换用/对接支持结构化引用的搜索 API（火山方舟 web_search）
2. 用 allowed_domains 限定官方域名（大麦 damai.cn、猫眼 maoyan.com、文旅部等）
3. 用 publish_time 做时效判断，替代自建 verified_at
4. 模型基于结构化 annotation 自己判断来源类型与时效
5. 表只在需要「跨会话复用核验结论 / 降低成本」时才引入，作为缓存而非数据源

用户要求参照豆包 web_search 做法配置票务 MCP。已产出 `.workbuddy-ai/memory/票务查询MCP方案-豆包模式.md`。

**核心：把豆包能力映射到用户架构，关键差异是「域名白名单只能在工具代码里判」。**

| 豆包 | 用户项目实现 |
|---|---|
| web_search 工具 | 新增 `search_ticket` MCP 工具 |
| allowed_domains | ⚠️ You.com 不支持，工具代码里 `extractDomain` + 白名单匹配 |
| annotations | 结构化返回 sourceType(OFFICIAL/UNVERIFIED) + domain + isStale + ageHours |
| user_location | city 参数拼进 query |

**技术事实（实测确认）：**
- 现有 `YouComSearchMcpExecutor.formatResults()` 只解析 title/url/description/snippets，**没解析域名、没解析发布时间**，拼成纯文本丢给模型
- You.com 无域名过滤参数（只有 freshness）
- You.com 是否返回 age/publish_time **不确定** → 阶段2必须先打印真实响应再写解析

**关键设计：**
- `sourceType` 只两档 OFFICIAL/UNVERIFIED（媒体/粉丝都归 UNVERIFIED，不做 MEDIA/FAN 档）
- 域名匹配处理子域名：`detail.damai.cn` 匹配 `damai.cn`（`endsWith("." + d)`）
- 排序 OFFICIAL 靠前
- description 必须写「不适用艺人个人资料（生日）」，防误用
- 默认 freshness=week（演出信息讲究时效）
- 白名单配置类 `TicketSearchProperties`（`starlineagent.ticket-search.official-domains`），改配置不碰代码
- 意图节点 kind=2，mcp_tool_id=search_ticket
- 与 youcom_search 并存：票务专用 vs 通用兜底

**system prompt 简化**：5 条核验规则砍成 3 句，因为 sourceType/isStale 已由工具算好。

**实施 4 阶段**：白名单判定(核心) → 时效判定(依赖age字段) → prompt简化 → 打通bad case

用户票务 MCP 选搜索源。五款国内联网搜索 API 关键信息（来源：2026-10-15 横评，公开资料，非第三方实测）：

## Jev（System One 决策模型）能否用于本项目的可行性分析（只读）

**是什么**：TypeSafe AI（前 OpenAI 研究员 Diogo Almeida 创办）2026-09-15 发布，定位 **System One Model**，**不生成文本**，只返回结构化判断。三类原语：
- `Noul`：布尔概率判断（返回 0-1 的 `noul` 值）
- `Choice`：多选一（≤255 候选，返回 `choice` + `confidence` + 全部候选的 `probabilities` 分布）
- `Score`：自定义量表打分（返回浮点 `score` + 各档概率）

请求结构 `{state: 原始上下文文本, questions: {名: {type, instructions, criteria}}}`；一个请求可批量提交多个 questions，耗时不随问题数线性增长（并行采样）。
官方自测：输入 0.042 USD/百万 token、**输出免费**、延迟 70-500ms、RLCD 概率校准（0.8 置信≈80% 真实正确率）、JSON 零格式错误。

**接入**：`POST https://api.typesafe.ai/v1/systemone`，`Authorization: Bearer TYPESAFE_API_KEY`，`pip install typesafe-sdk`；也支持 Vercel AI Gateway / Cloudflare Workers AI 转发、TypeSafe 官方 Skill 包。

**本项目可落点（按性价比排序）**：
1. **意图识别**（`DefaultIntentClassifier.classifyTargets`，rag/core/intent）——当前 `LLMService.chat` + temp0.1 + `LLMResponseCleaner.stripMarkdownCodeFence` + `parseScores` 容错（代码里已写「容错：模型又包了一层 results」，说明结构化输出不稳）。改为 `Choice`（criteria=各叶子节点描述）取 `probabilities` 全分布 → 零解析映射 `NodeScore`。注意项目需要**多标签**（多个 KB 节点同时命中），得靠概率阈值切片，不是取单一 best。
2. **替代 `overlap()` 判幻觉/相关性**（A3/A4 规则）——现在用 `overlap(answer, toolOutput) < 0.25` 这个魔法数字逼近语义判断，Jev `Noul` 可直接问「该工具输出是否支持该答案」，比字符级重叠准。
3. **bad case 根因预判**（`root_cause` 7 分类）——`Choice` 给「建议根因 + 置信度」，低置信转人工，契合既有「机器发现问题、人确认」设计。
4. **MCP 写操作动态 HITL**——现在 `require_confirm` 是 `t_intent_node` 上的静态开关；可用 `Noul` 判「本次参数是否涉及不可逆/跨用户写」动态决定是否要确认。
5. **评测断言判定**——现有 `expectAll/expectAny/forbidAny` 只做字符串/工具名匹配，判不了「是否忠实」。但 Jev 是弱模型，做裁判要警惕判不准。

**不建议用**：答案生成、query rewrite、摘要（不能生成文本）；时间/日期推理（官方明确不擅长，票务「下周五」别交给它）。

**三个必须先验证的坑**：
1. **国内可达性未验证**——TypeSafe 是美企，`api.typesafe.ai` 从广州机器出去大概率不稳；搜索未见国内云（百炼/方舟）托管 Jev 的证据（阿里云那篇文章结尾挂的是百炼推广链接，疑为广告）。**上线前必须先在生产服务器 curl 实测连通性与延迟。**
2. **非 OpenAI 兼容**——不能复用现有 `ai.providers`（`chat/completions` + `api-key` + `endpoints.chat`）机制；`LLMService` 只有 `chat/streamChat`（String↔String），需新增 `ModelProvider.TYPESAFE` + 新 Client + 新接口方法（如 `decide(DecideRequest)`），是真代码不是配置。
3. **准确率未验证**——官方自测不可信，必须用自有 bad case 集 A/B。

**成本量级**（粗算，需实测）：意图识别单次 input 约 2-5k tokens。DeepSeek 约 0.005 元/次，Jev 约 0.0006 元/次 → 差约 10 倍；延迟 70-500ms vs LLM 0.5-1.5s，意图识别在链路最前端每轮都跑，省 0.5s 体感明显。
