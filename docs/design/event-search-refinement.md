# 演出搜索增量改造（2026-11-09）

本次基于已上线的演出覆盖 v1 整合。2026-11-08 本地基线落后远端，因此未直接覆盖执行器或回退游标/行程契约。本地原型完整保存在 `backup/event-search-local-20261109` 分支。

## 行为

- 第一轮最多 6 个查询，包含音乐节/拼盘/加场；第二轮从艺人相关的结果（包括名单外线索）发现城市，定向查询启用的官方域名。名单外内容不能形成卡片。
- 总查询计划默认上限 12，原始结果预算仍为 200，多提供方、重试、熔断、缓存和有界线程池沿用 v1。提供方重试或翻页可能产生额外 HTTP 请求，查询计划数不等于计费请求数。
- 未指定城市时为第二轮预留搜索时间，并在剩余总预算内最多读取 4 个白名单 HTML 页面。优先提取当前艺人/城市的 JSON-LD Event；读取失败回退原搜索片段。
- 无城市发现总预算仍为 8 秒；指定城市查询仍为 3 秒且不读取详情，不扩大既有观演规划 4 秒边界。
- 明确的连续日期与标明场次数的区间可补齐中间日期；未说明逐日演出的区间沿用 v1 保守端点/未知规则；无年份不凭当前年份造确定场次。
- 无发布时间标记时效待核验；存在多个不同开票批次而无法映射场次时不随意提供一个提醒时间。
- 使用已有 391 城市字典、城市拆块、场次合并、稳定 `nextCursor` 和前端加载更多契约。没有改回旧 `offset` 分页，也不覆盖已上线前端/API/数据库。

## 配置与诊断

前缀 `starlineagent.artist-event-search`：`max-queries=12`、`read-details=true`、`max-detail-pages=4`、`detail-budget-millis=1000`。详情预算包含在原有 `discovery-timeout-millis=8000` 中，不额外叠加。其余配置沿用 [v1 实施说明](event-search-coverage-v1-implementation.md)。

`coverage` 新增 `detailAttempts`、`detailRead`、`detailUnavailable`；查询/过滤/来源/分页计数沿用现有格式。详情不可用不表示没有演出，也不把搜索片段误称为已经读取页面正文。
