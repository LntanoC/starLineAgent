# 明星社交动态订阅设计 v1：微博、抖音、小红书

> 日期：2026-11-14（Asia/Shanghai）。状态：设计草案，未实现、未部署、未完成真实账号采集验证。
>
> 目标：关注明星本人及工作室在微博、抖音、小红书发布的公开内容，通过企业微信群机器人接收通知。三个平台均为本次交付范围。

## 1. 方案结论与范围

采用“独立采集服务 + 星序订阅业务 + PostgreSQL 持久任务 + 企业微信通知”。星序负责账号身份、动态记录、订阅、投递和状态展示；采集服务封装平台变化。优先验证自建 RSSHub，无法满足数据契约的平台使用定制适配器或经验证的数据服务。

不把 RSSHub 当作三个平台均已接通的依据。不存在已确认可用、无需账号所有者授权的三平台统一官方接口。本方案尚未指定付费提供方，也不假设能取得明星本人授权。

### 1.1 首版内容

| 平台 | 首版监控内容 | 明确边界 |
| --- | --- | --- |
| 微博 | 本人/工作室新发微博，含图文、视频；转发可选，默认关闭 | 不含评论、点赞、关注变化、粉丝发言 |
| 抖音 | 本人/工作室新发布的作品，视频及图集按实测能力分别标记 | 不含直播开播、直播内容、评论、喜欢列表 |
| 小红书 | 本人/工作室新发布的图文及视频笔记 | 不含收藏、评论、点赞及私密内容 |

以管理员核验的账号清单为范围，不以艺人姓名搜索结果代替账号监控。首版不保证删除、编辑和瞬时发布后删除的内容检测；不做全网舆情监控。跨平台相同内容分别保留和通知，避免误合并。

首版提供逐条通知、暂停/恢复、发送记录；每日汇总、免打扰、AI 分类与演出信息提取留到后续版本。首版默认不依赖模型调用，不下载完整视频，不做视频转写。

## 2. 接入证据、选择与验证门槛

以下为 2026-11-14 查阅的文档/源码证据，只能说明接口约束及实现线索，不能证明目标账号在生产网络可采集。

| 平台 | 查阅结果 | 首选验证路径 | 不满足时的处理 |
| --- | --- | --- | --- |
| 微博 | RSSHub 博主路由存在，包含 Cookie、浏览器及反爬相关逻辑；部分博主需要登录才能访问 | 自建 RSSHub `/weibo/user/{uid}`，核对 UID、动态 ID、链接、发布时间及缓存 | 独立微博适配器或数据服务；官方 API 仅在实际应用权限及目标账号可访问性验证后启用 |
| 抖音 | 官方视频列表文档要求申请权限及用户授权；小程序作者视频列表也要求作者授权绑定。RSSHub 博主路由使用浏览器读取作品响应 | 无明星授权时验证 RSSHub `/douyin/user/{secUid}`，记录视频/图集分别覆盖情况 | 定制采集或数据服务；取得作者授权后再评估官方接口，不预先绑定旧 API 路径 |
| 小红书 | RSSHub 用户笔记路由存在 Cookie/浏览器分支；所查无 Cookie 分支以标题作为 GUID，链接可能指向封面，未提供可靠发布时间 | 验证 `/xiaohongshu/user/{userId}/notes` 的实际输出，必须获得笔记 ID、笔记原文链接和时间证据 | 不合格 RSS 只作发现线索；补充详情解析或切换数据服务，禁止直接用标题 GUID 触发通知 |

特别注意：Cookie 是访问凭证，不代表获得作者 OAuth 授权；粉丝登录自己的账号不能替代抖音作者授权。公开网页可访问也不等于采集方式及规模已获平台许可，具体接入方式需核对平台规则和实际授权范围。

小红书官方开放平台页面本次未取得可读接口正文，不能据此断言存在或不存在任意用户笔记查询能力；不采用尚未核验的第三方接口描述作为官方能力依据。

### 2.1 三平台均须完成的验证表

每个平台选择目标明星实际账号；存在工作室账号时一并验证，另用近期活跃账号辅助观察。逐项记录账号、采集器版本、时间、部署网络和脱敏样例：

1. 账号稳定标识与管理员核验的身份一致，昵称变化不创建新账号。
2. 可提取稳定作品 ID、作者 ID、原文链接、内容类型；发布时间可核对来源。缺失字段不得由模型补造。
3. 置顶、同名标题、分页、登录过期、验证页、错误页、空列表能正确区分。
4. 明确返回窗口、分页能力、上游缓存时长，检查一次轮询间隔内多条更新是否会丢失。
5. 连续运行至少 7 天，与人工查看的同一范围逐项比对；观察期无新作品时不能证明新增通知成功，须补充活跃账号观察或等待真实新增。
6. 三平台分别形成“通过/待验证/不可用”的结论。任一未通过，就不能把整体标记为三平台已上线。

数据服务候选还需验证数据来源与使用范围、ID稳定性、发布时间语义、缓存、分页、错误码、额度、价格和退出迁移方式；购买和传递凭证不属于本次设计交付。

## 3. 用户流程与界面

1. 管理员创建艺人，录入微博/抖音/小红书账号主页，核验本人或工作室身份；账号在基线成功前显示“初始化中”。
2. 用户进入“动态订阅”，选择艺人，勾选平台、本人/工作室和微博转发选项。未接通的平台可保存为“等待接入”，单独显示状态，不能显示监听正常。
3. 用户在通知设置中保存企业微信机器人 Webhook，可手动发起一次测试。测试会发送真实群消息，按钮应写明“发送测试消息”。
4. 新订阅默认从生效后开始，界面明确“历史内容仅展示，不补发通知”。新增加的平台账号也先建基线。
5. 动态流展示平台、账号角色、原文摘录、原文链接、发布时间和发现时间；未知发布时间明确显示“未知”。同时展示每个平台最后成功检查时间及采集异常。
6. 用户可暂停、恢复或取消订阅，查看待发送/接口已接收/失败/已取消记录。恢复默认从恢复后开始，不补发暂停期间内容。

“接口已接收”只表示企业微信返回成功，不代表群成员已读。用户页展示业务状态；Cookie、采集器内部配置和重试堆栈只在管理端展示脱敏信息。

通知模板：

```text
某某发布了新动态 · 小红书
账号：某某工作室
发布时间：2026-11-14 14:32（北京时间）
内容：原文摘录……
查看原文：https://平台原文地址
```

首版使用截断的原文摘录，标为摘录。后续 AI 摘要需单独标注，生成失败回退到摘录，不阻塞通知。

## 4. 架构与当前项目集成

```text
星序前端：动态流 / 我的订阅 / 通知设置
                   │
starline/social：账号管理、订阅、查询、采集调度、投递调度
        │                        │
        │                        └─ 企业微信固定域名 Webhook
        ├─ PostgreSQL：账号、动态、事件、订阅、投递任务、运行记录
        └─ 内网采集服务
              ├─ 微博适配器 ── RSSHub / 定制 / 数据服务 / 授权 API
              ├─ 抖音适配器 ── RSSHub / 定制 / 数据服务 / 授权 API
              └─ 小红书适配器 ── RSSHub / 定制 / 数据服务 / 授权 API
```

- 当前 `bootstrap` 已开启 Spring 调度，`starline` 有活动/日历控制器与服务；沿用既有登录上下文和响应包装。
- 业务代码建议放 `starline/.../social/`，前端新增动态订阅页及服务文件。既有平台来源白名单描述平台域名与演出查询能力，不作为明星账号表或通知渠道表。
- 动态采集独立于 Agent 会话持续执行。Agent 后续可查询动态或引导到订阅表单；创建群通知订阅应走明确的用户操作。
- 浏览器采集放在内网独立容器，限制资源，避免采集卡住拖垮 API。RSSHub 由采集服务访问，首版不开放公网任意 RSS URL 输入。
- 第一版用 PostgreSQL 任务表，无需引入新消息中间件。已有 Redis 可辅助平台并发/速率限制，数据库约束仍为去重与任务一致性的依据。
- RSSHub 或定制采集器应固定版本；升级先回放脱敏样例及跑目标账号验证，再切换线上版本。

### 4.1 统一采集契约（设计）

```text
fetchAccount(account, checkpoint, budget) -> FetchResult

FetchResult:
  platform, accountIdentity, provider, providerVersion
  fetchedAt, upstreamObservedAt?, cacheAgeSeconds?
  items[], nextCursor?, hasMore, coverage, errorCode?

FeedItem:
  platformPostId, authorPlatformId, canonicalUrl
  kind, title?, textExcerpt?, publishedAt?, sourceUpdatedAt?
  observedAt, timeEvidence, contentCompleteness

coverage = WINDOW_COMPLETE | PARTIAL | UNKNOWN
errorCode = AUTH_EXPIRED | CHALLENGE_REQUIRED | RATE_LIMITED |
            SCHEMA_CHANGED | ACCOUNT_UNAVAILABLE | NETWORK_ERROR
```

`WINDOW_COMPLETE` 仅指声明的本次时间窗口完整，不代表账号全部历史。只有作品 ID、作者及可回到原文的链接可靠时才进入正式动态库；缺 ID 的条目进入隔离记录，不能降级用标题或正文哈希充当作品 ID。

RSS GUID 不天然等于作品 ID，需平台适配器解析验证；封面 URL 不能充当原文链接。获取不到发布时间的条目可以作为“首次发现、时间未知”展示，首版不自动推送；以免把置顶历史作品当作新发布。

## 5. 采集、基线与漏采边界

### 5.1 调度默认值（待实测调整）

| 参数 | 起始建议 |
| --- | --- |
| 账号轮询 | 10 分钟，加入约 ±20% 抖动；按平台额度调整 |
| 调度扫描 | 每 30 秒领取到期账号 |
| 采集超时 | 每账号总预算 60 秒，平台并发起步为 1 |
| 平台限速 | 包括详情补全等全部上游请求，由适配器报告实际消耗 |
| 临时故障退避 | 5、15、60 分钟；持续失败转异常并通知管理员 |
| 登录/验证异常 | 暂停自动高频尝试，等待维护恢复 |

这些数值是运行初值，不是平台允许额度或实时 SLA。有效发现延迟包含轮询、上游缓存、采集和排队；上游缓存未知时不承诺十分钟必达。调度应设平台和账号总预算，超出时显示排队延迟。

### 5.2 首次基线

无活跃订阅或未完成初始化的账号不运行正常通知流程。初始化先拉取声明窗口，将看到的 ID 记为基线，成功后原子记录 `baseline_completed_at` 和账号代次。失败保持“初始化中”，不把空响应当作基线完成。

全新账号首次接入、长期停用后重新接入或更换不能证明窗口连续的数据源，都需重新评估基线。切换来源沿用平台作品 ID，不因提供方 ID变化重复通知；不能建立 ID 对应关系时保持待核验。

已在运行的账号新增订阅不重置公共基线；每个订阅单独保存 `active_since`。暂停/恢复递增订阅代次并重设生效时间，旧代次未发送任务被取消。

### 5.3 正常增量与补采

- 同一平台账号采集一次，服务所有订阅用户；按平台作品 ID 去重，置顶顺序和统计数变化不产生新发布事件。
- 每轮重读最新窗口，支持分页的来源追到上次已确认边界，并保留重叠窗口，避免乱序和延迟可见导致漏采。不能在第一页遇到一条旧置顶就停止。
- 有发布时间证据且在账号基线、订阅生效之后的新 ID才能触发首版通知。所有时间持久化为带时区时间，界面转北京时间；来源时间精度低时保守标为待核验。
- 来源有分页预算但尚未完成时，保存续采进度，覆盖标记 PARTIAL，不推进“完整覆盖至”水位。永久只有首页的源只能声明首页覆盖。
- 故障后补采最近 24 小时内可取得的新增，消息标注“延迟发现”；更早的只入库展示，不集中刷群。24 小时为可配置产品策略，不代表采集能力。
- 断线超过来源保留窗口、命中页数上限或源无法分页时，明确记录可能漏采区间；恢复成功不自动清除历史覆盖缺口。
- 一次不出现某作品不能推断已删除；空列表、验证页、字段变化不能更新成功时间或清空历史。

## 6. 数据结构与一致性

以下为逻辑表设计，具体 DDL、索引及迁移在实施阶段补充，表名前缀采用 `t_starline_social_`。

| 表 | 关键字段/约束 |
| --- | --- |
| artist | id、name、aliases；管理员维护艺人 |
| account | artist_id、platform、platform_user_id、profile_url、role、identity_evidence、provider_config_ref、status、baseline_completed_at、checkpoint、last_attempt_at、last_success_at、next_poll_at、lease_owner、lease_until、lease_version；唯一(platform, platform_user_id) |
| post | id、account_id、platform、platform_post_id、canonical_url、kind、excerpt、published_at、first_seen_at、time_evidence、completeness、content_hash；唯一(platform, platform_post_id) |
| event | post_id、event_type、account_generation、created_at、fanout_cursor、state；唯一(post_id, event_type)，首版仅 PUBLISHED；作为持久分发事件 |
| subscription | user_id、artist_id、channel_id、platforms、account_roles、include_reposts、status、active_since、generation；唯一(user_id, artist_id, channel_id) |
| channel | user_id、type=WECOM_ROBOT、name、encrypted_webhook、key_version、config_version、status、last_test_at；保存者独占管理 |
| delivery | event_id、subscription_id、subscription_generation、channel_id、channel_config_version、state、attempt_count、next_attempt_at、lease_version、lease_until、response_code、sent_at；唯一(event_id, subscription_id, subscription_generation) |
| collection_run | account_id、started_at、finished_at、status、source_count、accepted_count、quarantined_count、new_count、coverage、failure_code、trace_id；不保存秘密值 |

凭证只存配置引用；Cookie、提供方密钥、OAuth Token放部署侧秘密配置或加密存储，不能直接塞进公开账号配置。Webhook 使用应用层加密，主密钥不入库。

一致性处理：

1. PostgreSQL 短事务领取账号并设置租约，事务外采集；完成时校验租约版本，旧 worker 不能覆盖新 checkpoint。
2. 新动态、PUBLISHED 事件和本轮可推进的 checkpoint在同一事务提交。只有插入成功且满足基线/时间策略的新动态才生成事件；事务失败不推进水位。
3. 分发 worker 分批匹配订阅，插入 delivery 与更新 fanout_cursor 同事务。崩溃可重放，唯一约束防止重复生成任务。
4. 投递 worker 用短事务加行锁/`SKIP LOCKED`领取任务，事务外请求企业微信；租约到期可重领，写回需校验版本。领取前检查订阅代次、渠道版本与状态，避免退订或变更凭证后的旧任务继续执行。
5. 分发匹配以发布时间及 `active_since` 为边界；晚加入的订阅不收到积压旧事件。用户取消后停止新任务，发送前再次检查；已经发出 HTTP 请求的消息不能撤回，此边界在界面说明。

首版仅支持用户自有渠道，不跨用户合并通知；多人分别配置同一个群 Webhook 可能产生多份通知，建议每群由一个订阅负责人配置。以后可独立设计共享群订阅和权限。

## 7. 企业微信投递设计

- 首版用机器人 Markdown消息，包含艺人、平台、账号、发布时间、摘录和原文链接。按当时官方字节限制截断，控制字符及 Markdown做转义，避免原文触发无意的 @所有人。
- HTTP 成功不等于业务成功，需解析企业微信响应业务码；只有明确成功才能记录“接口已接收”。
- 限流以实际机器人 key 的服务端 HMAC 指纹为维度，跨 worker、跨保存记录共享；起步预算设为每分钟 15 条并平滑发送，低于已查阅接入资料中的 20 条/分钟上限，正式上线前复核官方说明。
- 短期超限保留在队列。超过积压阈值先显示延迟和通知维护者；首版不临时改为未经用户选择的汇总模式。
- 网络异常和可重试业务码按 1、5、15、60 分钟退避，共最多 5 次请求。不可恢复错误直接失败并标记渠道异常；手动重试需提示超时记录可能已送达。
- 超时结果记录为 UNKNOWN，可有限重试。Webhook 无本项目可依赖的外部幂等凭证，不能承诺端到端恰好一次；内部任务去重不能消除外部已接收但响应丢失的重复。
- 更换 Webhook或停用渠道递增配置版本，取消未领取的旧版本任务；新增和变更均可独立测试。无更换授权时不自动把积压消息投到新群。

### 7.1 权限与请求边界

订阅、渠道、投递查询均校验登录用户归属；管理员维护账号，不读取用户 Webhook明文。Webhook 仅接受 HTTPS、精确主机 `qyapi.weixin.qq.com`、预期端口/路径和 key 参数，拒绝自定义主机与重定向，服务端固定请求模板，不执行任意回调 URL。

账号输入解析为各平台标识，再由适配器生成固定域名请求；短链接需逐跳验证，禁止访问本机、内网、云元数据地址。RSSHub 内网访问只允许预配置服务和路由模板。原文 HTML不直接注入前端。

日志与审计不记录 Webhook key、Cookie、Authorization、完整带签名 URL。脱敏样例保留结构而不保留会话凭证；凭证泄漏可撤销或轮换。

公共前缀沿用 `/api/starlineagent`；下列为设计路径，尚未实现。所有列表分页并限制 pageSize，修改操作沿用既有身份与审计机制。

| API | 用途 |

## 9. 观测、容量与留存

首版建议软配额：全局监控账号 30 个，每用户 20 个艺人订阅、3 个通知渠道；超过配额需显式提示并由管理员调整。没有活跃订阅的账号停止常规轮询，恢复按第 5 节建立安全边界。

30 个账号按 10 分钟检查约 4,320 次账号检查/日；一次检查可能触发多次上游请求，详情补全、重试和分页需另计。成本应按“上游请求量 × 单价 + 浏览器容器资源 + 存储”核算，未选数据服务前不报固定月费。

建议记录：每平台成功率、最后成功间隔、验证/过期次数、实际缓存年龄、覆盖缺口、隔离条目数、发现延迟、任务积压年龄、业务发送成功率和 UNKNOWN次数。成功率分母必须含失败/受限账号，不能把它们排除后展示全绿。

首版内部目标（只用于验证，不对外承诺）：采集健康且上游缓存已知时，发现延迟 P95 ≤ 20 分钟；无拥塞时入库到企业微信接口接收 P95 ≤ 60 秒。业务成功率需剔除明确取消任务但保留业务失败，外部已读率不可测。

采集运行/脱敏诊断和投递明细默认保留 30 天，动态摘录默认 90 天。监控期间保留最小作品 ID去重记录，避免内容清理后置顶重发；账号彻底删除后按保留政策清理。原始响应默认不长期保存，排错样例设大小和有效期限制。

## 10. 实施顺序与验收

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| A：三平台采集验证 | 每平台目标账号、字段样例、缓存/分页/登录依赖、提供方选择、成本估算 | 三平台分别通过第 2.1 节；不合格源明确替换方案，不用模拟数据充当已接通 |
| B：订阅与投递骨架 | 表结构、账号管理、订阅、渠道、持久事件和投递状态机 | 用脱敏回放验证初始化、并发去重、崩溃恢复、用户隔离、取消和失败重试 |
| C：三平台联合试运行 | 真实采集、订阅页、企业微信消息和管理状态 | 三平台都出现真实新增到群的记录；用户手动配置渠道并明确启用测试/试运行 |
| D：正式上线 | 监控、运行手册、数据库迁移、回滚说明 | 完成目标账号观察与人工对照，已知缺口公开展示；按实际用户授权执行部署 |

关键验收场景：

1. 首次订阅看到历史动态但群内不刷历史；同标题不同 ID的新作品可分别通知。
2. 同一作品重复返回、置顶/取消置顶、刷新统计、重启、双 worker 并发不重复创建 PUBLISHED事件和正常投递任务。
3. 一轮多作品、分页中断、延迟可见、上游缓存、超过窗口的断线恢复均有明确处理与覆盖状态。
4. Cookie 失效、验证码/验证页、结构变化、空列表不显示“没有新动态”；小红书标题 GUID/封面链接被隔离。
5. 插入后分发前、分发中、发送后确认前进程退出，任务可恢复；发送超时如实为 UNKNOWN并显示重复风险。
6. 超限、业务错误、永久失效、退订、暂停恢复、轮换 Webhook、多用户共用机器人 key均有回放验证。
7. 用户不能读取或改动他人的订阅和渠道；请求不能被输入 URL引向任意服务；日志中无凭证。
8. 企业微信消息包含正确艺人、账号、平台、原文链接和来源时间；未知时间不伪造，接口成功不表述为用户已读。

实施时为每个平台保留独立启停开关。故障可停单个平台，保留订阅、历史和覆盖缺口；整体停用时停采集与新投递，不删除既有活动/日历数据。数据库采用向前兼容的新增表迁移，首次回滚以关功能为主。

## 11. 后续增强

- 每日汇总、免打扰、群级共享订阅和跨平台同内容聚合，需分别定义分组与权限，不混入首版逐条投递状态机。
- AI分类/摘要与演出线索提取可异步运行，不影响原始动态通知。提取结果为待核验候选，不直接写为已核验开票提醒；沿用当前星序活动的来源核验和时间约束。
- 直播与编辑/删除提醒另作事件类型，先证明各平台确实可观察，再增加产品承诺。
